# 浏览器动作必须读回状态：越权勾选、静默吞错与证据分隔符

## Context

2026-10-19 21:00 第 3 段跑通并真发成功之后，我在读回账本与表现数据时发现四处缺陷。
其中三处同源：**页面动作执行了，但没人验证它真的产生了期望的效果**。

这不是某一处写错，而是一个反复出现的形状：

- ADR-0034 记录过「包装层漏传 `--no-weitoutiao`」，判定为包装层疏漏；
- ADR-0045 记录过「反查把截断的 stdout 当未找到」；
- ADR-0046 记录过「声明勾没勾上没人知道」。

三次都被当成孤立事故各自修掉，但**第四次又以同一个形状出现**：10-18 那篇实际
发了两条内容（文章 + 微头条），而系统全程认为一切正常。

## 发现

### 一、`uncheckWeitoutiao()` 把微头条勾上了，而不是取消

`reference/toutiao-ops/cli/src/publish-article.js` 原文：

```js
async function uncheckWeitoutiao(page) {
  try {
    // "同时发布微头条" 默认已勾选，点击取消
    const checkbox = page.locator('text=发布得更多收益').first();
    await checkbox.click({ timeout: 5000 });
    await sleep(200, 400);
  } catch {
    // 取消失败不阻塞
  }
}
```

注释断言「默认已勾选」。**这个断言是错的。** DOM 探针在发布页实测：

| 时刻 | 「发布得更多收益」状态 |
| --- | --- |
| 全新打开页面（两次） | 未勾选 |
| 填完标题 | 未勾选 |
| 填完正文 | 未勾选 |
| 再等 3.5 秒 | 未勾选 |
| 点击一次 | **勾上** |
| 再点一次 | 回到未勾选 |

也就是说 `uncheckWeitoutiao()` 是个 **toggle**，而它的输入在初始态是「未勾选」。
一次 `--no-weitoutiao` 的调用，实际效果是**把微头条勾上**。

推论：ADR-0034 把 10-14 那次多发判定为「包装层漏传参数，不是上游缺陷」是**错的**。
`publish.py` 一直传了 `--no-weitoutiao`（`publish.py:376`，且 `index.js:68` 声明了
该选项），修完 10-14 之后 10-18 仍然多发了一条——如果根因是漏传参数，
这种情况不该发生。真正的根因是那次点击本身。

10-17 没多发，只是因为 click 抛了异常被 `catch {}` 吞掉；10-18 没抛，就勾上了。
**同一段代码在不同时刻给出相反结果，而且两种结果都报告成功。**

### 二、微头条在数据层冒充「我们的文章」

`content list` 把文章和微头条混在同一个列表里返回，两者平台侧字段的差别是：

| 判据 | 文章 | 微头条 |
| --- | --- | --- |
| gid 位数 | 19 位 | 16 位 |
| URL | `/item/<gid>/` | `/a<gid>` |
| `content` 字段 | 空 | **非空**（内容就是正文/标题） |

因为标题相同，`performance.py` 的 `latest_per_article()` 按 gid 去重时把它们算成
**两篇**。实测 `reports/performance.jsonl` 里 10-18 那篇有两个 gid
（`7697993836580045347` showCount 134、`1879393099729987` showCount 3），
后果是冷启动豁免「5 篇」（ADR-0010）被提前消耗、基准被一条数字极小的记录稀释。

### 三、`--evidence` 用逗号分隔，把证据本身切碎了

`run_all.sh` 把 `event.key_evidence` 拼成逗号分隔字符串传给
`writeback.py --evidence`，后者 `split(",")`。但证据文本自身含英文逗号：

```
掘金实测：… 生成 16,735 字节、71.7 秒、1.22 credit，V4-Pro 为 9,906 字节 …
```

一次写回把这条证据切成 8 段，直接写进了 `knowledge/cards/llm-price-war-signals-commoditization.md`
的修订史（`16` / `735 字节`、`9` / `906 字节`、`15` / `349`、`21` / `333`）。
**千分位逗号是中文技术写作里的常态，用逗号做分隔符从一开始就选错了。**

### 四、已恢复的源永久留在 `failures` 里

`collect.py` 的 `merge_candidates()` 只排除「本次也失败」的源，不排除「本次已恢复」的源：

```python
failed_sources = {f["source"] for f in fresh.get("failures", [])}
failures += [f for f in existing.get("failures", []) if f["source"] not in failed_sources]
```

10-19 实测：08:07 与 13:00 两次 csdn/sspai 报 HTTP 500，18:05 成功
（`counts.sources_ok: 7, sources_failed: 0`），但合并后的 `failures` 仍带着它们。
简报因此同时印出「源：7 成功 / 0 失败」与「**失效源**：csdn, sspai」——
两句话互相矛盾，而读的人会信后一句。

## Decision

1. **凡是对页面状态有期望的动作，必须读回状态再判定。** 具体到微头条：
   `uncheckWeitoutiao()` 改为「读 class 状态 → 只有确实已勾选才点击 → 点后读回再验」，
   失败时 **抛异常**（不再 `catch {}` 静默通过）。勾选框状态的唯一可靠来源是
   `label.byte-checkbox` 的 className 是否含 `byte-checkbox-checked`：
   该元素**没有原生 input、没有 aria-checked**。
2. **声明勾选改为「点后读回、未勾上则报错」。** 声明是法规义务（ADR-0046），
   静默失败等于「系统不知道自己在做什么」。同时发现声明之间是**单选互斥**
   （点「个人观点」后再点「引用AI」，前者自动取消），因此逗号分隔多值只有最后一个
   生效——这一点也显式报错，避免上层误以为传多个就都生效。
   它修正了 ADR-0046 里「技术上可以同时勾」的推断：DOM 上不行。
3. **`--no-weitoutiao` 每次都传，不因上游已修而省略。** 发布页是平台页面，
   它的默认值随时会变；唯一可靠的姿态是每次都显式要求不要。
4. **反查同时数「同一标题下有几条文章、几条微头条」**，写入账本 `verify_kinds`，
   出现微头条时置 `weitoutiao_leak` 并在简报 ⑤ 段列出。
   反查只问「标题出现没有」，量不出「多发了一条」——这正是 10-14 与 10-18
   两次都判 `title_found` 的原因。
5. **`performance.py` 与 `brief.py` 都排除微头条**，判据与第 4 条同一套
   （gid 位数 / URL 形态 / `content` 是否非空，三票取多数）。
   老记录没有 `kind` 字段，按 gid 位数回退判定——`reports/performance.jsonl`
   是跨环境保留的入库文件，只认新字段等于没修。
6. **证据分隔符改为换行。** `run_all.sh` 的 `dec_field` 默认 `"\n".join`，
   `writeback.py` 改为 `split("\n")`。逗号不是安全分隔符：证据文本本身含英文逗号
   （千分位、并列句）。参数语义的变更记录在 `--evidence` 的 help 里。
7. **`collect.py` 合并时排除「本次已恢复」的源**，且 `counts.sources_failed`
   取合并后 `failures` 的长度，让「失败数」与「失效源列表」永远自洽。

## Consequences

**ADR-0034 的结论被推翻，但它的记录保留。** 我不改写历史 ADR——那会让「当时为什么
这样判断」消失。ADR-0034 顶部标注「根因判断已被 ADR-0047 修正」，正文保持原样。
这是 ADR-0017「已发布内容不自动修改」的同一精神：判断可以推进，但不涂改。

**这四处缺陷里只有第 3、4 条是纯逻辑错误，前两条的根因是「沉默」。**
`catch {}` 与「不读回」是同一个问题的两种写法：代码假装自己做完了。
真正贵的不是修 bug，是**发现它在沉默**——10-14 与 10-18 之间隔了四天，
系统每天都报告成功。

**微头条删不掉。** `content-manage.js` 只导出 `listContent()`，CLI 没有删除能力。
已发出的那两条只能在后台手工删。账本已回填 `weitoutiao_leak` 与 `corrected_at`，
标为「已发生、未修复」。

**「读回」会成为后续所有浏览器动作的默认要求。** 这条 ADR 的真正约束不是那三处
代码，而是下次写任何 `page.click(...)` 时的第一反应：**我怎么知道它生效了？**
如果答案是「因为它没抛异常」，那就还没做完。

**残余风险：读回本身也可能读错。** 我们读的是 className，平台改版会让它失效。
缓解是三条判据取多数而不是单条（第 5 条），但这只让失效退化成「仍大致正确」，
不能消除。真正的兜底仍然是人工偶尔看一眼后台——ADR-0008 的分工没有变。
