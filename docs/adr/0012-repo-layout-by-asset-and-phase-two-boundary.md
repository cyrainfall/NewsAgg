# 仓库按资产类型分目录，多平台延后到第二阶段

## Context

仓内需要安放的东西已经明确：观点卡、成稿与教学副本、简报、风格资产、平台配置，以及 wewrite 的状态目录。

两种自然的分法："按资产类型"分，或"按流水线阶段"分（与采集/分拣/发布/简报四个技能一一对应）。后者看似更贴合系统的结构，但会造成一个实际问题：认知资产会散落在"分拣阶段"的目录下，而它恰恰是本人日常最常翻阅、最常修改的东西。资产的可寻性比阶段映射更重要。

同时需要明确一个范围边界：用户最初提到"今日头条、小红书等平台"，但第一阶段定为只做头条，且"平台稿"这一概念已因头条的文章本身就是长文而被删除。

## Decision

**目录按资产类型划分**：

```
knowledge/cards/    观点卡（认知资产）
outputs/            成稿 + 教学副本
reports/            简报 markdown（与 issue 双写）
style/              风格资产
platforms/          平台配置（如 toutiao.md）
plugins/newsagg/    插件源码（安全门 + 受限 Tool + 面板，见 ADR-0025）
reference/          参考仓库（8 个 vendored 项目，git 排除）
.agents/skills/     自建技能（采集/分拣/发布/简报）
.wewrite/           wewrite 状态目录（WEWRITE_HOME 指向此处）
```

**参考仓库移入 `reference/` 并从 git 排除**：`reference/` 下的 8 个 vendored 仓库加进 `.gitignore`，不提交。理由是其中包含 `DailyHotApi/node_modules` 与 `xiaohongshu-skills/.venv` 这类体量巨大的目录，提交会让仓库变成 GB 级、clone 与 CI 都不可用；而它们只需要本地可读以作参考。这意味着参考代码不可重现，需要时可重新 clone——这是有意的取舍。

**多平台延后到第二阶段**：第一阶段只发今日头条。"平台稿"概念在引入第二个平台时重新引入，届时需要重新回答"母体与派生"的关系。

## Considered Options

- **按流水线阶段划分**（`ingest/` `triage/` `publish/` `brief/`）：职责映射清晰，但把最常被人翻阅的认知资产埋进某个阶段的目录里。
- **全平铺**：最扁，但卡库与成稿增长后难以查找。

## Consequences

- 简报**双写**：既开 GitHub Issue（可评论、有通知入口），也写 `reports/` 下的 markdown（随 git 永久可追溯）。两者职责不同，不是冗余：issue 是人机交互界面，markdown 是历史档案。
- 由于认知资产与简报都在仓内，且本人通过修改成稿来教学（ADR-0008），**仓库就是人机交互的主要界面**，而不只是代码存放处。这使 `git pull` 成为本人查看系统状态的主要动作。
- 多平台延后是一个**有意的范围收缩**，不是遗漏。未来若有人问"为什么没有小红书"，答案在此。重新引入平台时，"母体文章/平台稿"的区分需要重新论证——它在只有头条时不成立，在有两个形态不同的平台时会重新成立。
