# 表现数据接回分拣作为排序参考，并驱动自动降频

## Context

成功判据是阅读与互动数据（Q24），且数据通过浏览器会话读回（Q41）。但数据回来后系统该做什么，最初没有定义——等于建了一个传感器却没有接到任何执行器上，而"获得关注"这一原始目标恰恰依赖这个回路闭合。

同时有两个约束：产出上限是每日一篇，因此样本量极小；平台社区规范把"批量发布低质内容"列为打击对象，因此持续产出低质内容本身是风控风险。

## Decision

表现数据以两种方式接回行为，且都不采用硬规则：

- **排序参考**：在简报中列出哪些观点卡与选题跑出了数据，并在分拣时把历史表现作为排序参考之一。不据此自动降权或退役卡片。
- **自动降频**：连续多篇文章的表现明显低于自身基准时，自动降低发文频率（如改为隔日）并告警，把"产出持续变差"当作故障处理。恢复同样需要人工确认。

## Considered Options

- **硬规则（表现差的卡自动降权/退役）**：反馈最强，但每日一篇的样本量下，极易把运气当作规律，并且会让卡片库因噪音而失去稳定性。
- **只记录、不改变行为**：工作量最小，但系统的改进将完全依赖人主动阅读简报并介入，与"自动化"的初衷相悖。

## Consequences

- 该回路有意保持"软"：系统会因持续低迷而降频，但不会自动认为某个议题是错的。判断议题对错仍属人的职责。
- 自动降频使系统在变差时会**变得更不活跃**，因此产出下降本身会掩盖问题的严重性——必须靠告警补偿，否则会静默滑向长期停摆。
- "自身基准"需要一个冷启动豁免期：新号首周的数据几乎必然很低且无参考价值，因此**首周的成败判据是链路是否跑通与本人是否愿意署名**，不是阅读数据。基准须在积累若干篇之后才建立。
- 表现数据只经浏览器会话读取（Q41），因此该回路的可用性与发布链路的可用性绑定在一起：浏览器一失效，连"系统表现如何"也一起失明。
