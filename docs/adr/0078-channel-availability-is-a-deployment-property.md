# 渠道可用性是部署属性，要声明，不要猜

## Context

2026-10-27 把主环境迁到服务器（ADR-0077）。服务器不装代理（用户定案：不动服务器网络）——于是 `r.jina.ai` 直连不通。

但这件事在系统里的**表现**是：体检说 `web` 渠道正常。

这不是体检坏了。`agent-reach doctor` 回答的是「这个渠道此刻能不能连上」——在本机上它能连上，在服务器上它连不上，两次体检各自都是**如实的**。问题在于：**渠道可用性根本不是代码属性，是部署属性**，而我们的系统里没有任何地方记录「这次部署用哪些渠道」。

后果具体是什么：ADR-0059 残余风险 53 早就记下了「Jina Reader 无代理会带着绿色状态失效」。在服务器上，这个风险从「可能」变成了「已经」——而系统**不会告诉你**。写作阶段如果按「web 渠道可用」的假设去取正文，会取到空，或者拿到一个「请允许执行 JavaScript」的页面（这正是 10-19～10-25 期间头条 trending 页抓不到正文的那个现象）。

## Decision

**渠道策略写成部署级文件 `deploy/channel-policy.txt`，运行时读它。**

### 一、为什么是文件而不是代码

如果写进代码：「web 渠道在本部署不可用」就成了整个系统的属性，而它只对某个部署成立。写进文件：

- 本机：`deploy/channel-policy.txt` 存在但可以声明 enabled（或者干脆不声明）。
- 服务器：同一份文件声明 disabled。

差别只有一行，但**归属完全不同**：前者是「这个渠道在这次部署里不能用」，后者是「这个渠道在这个系统里不能用」。

### 二、为什么不让体检自己去说

体检能回答「此刻能不能连上」，不能回答「我们决定不用它」。这两件事必须分开，因为它们对读者的意义不同：

| | 含义 | 要人做什么 |
|---|---|---|
| `disabled` | 我们主动关掉的 | 知道今天的采集面少了一块，正文从别处取 |
| `off`/`error`/`warn` | 它自己坏了 | 去查、去修 |

混在一起会犯两个错：把「我们关的」说成「它坏了」，人去查一个根本没坏的东西；把「它坏了」混进「我们关的」，人以为已经处理过了。

所以简报第 ⑤ 段现在有两种措辞：`○ web：…（不是故障）` 与 `✗ GitHub：…`。

### 三、关掉的渠道不计入可用率的分母

一个已知不可用的渠道每天挂在「tier-0 4/5 可用」的分母里，会让这个数字永远不回到 6/6，而第 ⑤ 段每天都挂着一个**已经处理过**的项。久而久之整段被无视——这正是 ADR-0021 边界二当初只报 tier-0 的同一个理由：第 ⑤ 段是「需你介入的事项」，堆噪声等于让这一段失效。

所以：声明关掉的渠道**从分母里拿掉**，但**单独列出来**说明。

### 四、判据是「实测过不通」，不是「我觉得不通」

策略文件里每条 disabled 必须写理由，且理由要能指到一次实测。当前这条的实测是：2026-10-27 在服务器上 `curl` 直连 `r.jina.ai` 不通，而 `www.google.com` 也不通（说明不是 Jina 单独的问题，是没代理）。

**这个「实测过」的要求是硬性的。** 一个凭感觉标上的 disabled，会在某天有人装了代理之后继续被当成「不可用」——而那时候它其实已经能用了，且没有人会想到去改策略文件。

### 五、没做的

**没做「自动探测 + 自动写策略」。** 听起来更聪明，但它会制造一个循环：策略影响体检 → 体检影响策略。声明式的东西一旦开始自己改自己，就没人知道它现在为什么是这样。策略是人的决定，机器只负责读。

## Consequences

- 渠道可用性有了唯一的真相来源，且它跟着仓库走（本机与服务器看同一份文件）。
- 简报第 ⑤ 段现在会说清楚「今天少了一块采集面，原因是 X」——**这正是 ADR-0059 残余风险 53 想要的**。
- 新增一条纪律：**部署到新环境时，要过一遍这个文件**。`bootstrap-server.sh` 的 `--check` 模式里应该加一项「渠道策略是否与本机网络相符」——今天没加（还没写），记为待办。
- 策略文件目前只有一条规则（web/Jina）。随着信源面变化它会长大；它长到十几条时就需要重新审视「tier-0 是不是还只有这六个」。
