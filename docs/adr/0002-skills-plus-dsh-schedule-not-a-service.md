# 用 Skills + DSH 定时任务实现流水线，不自建常驻服务

## Context

流水线需要在云服务器上无人值守运行。最直觉的做法是写一个常驻服务（Python/Node + cron），自己实现调度、状态、重试、告警与模型调用。

但本工作区已经存在一整套可直接加载的资产：`.agents/skills/` 下 48 个技能，包括 `ybrain-*`（捕获/组织/提炼/表达四段式方法）、`xiaohongshu-skills`（CDP 接管已登录浏览器的完整实现，含 `human.py` 拟人节奏与 `risk_analyzer.py`）、以及 `wewrite-*` 内容流水线。宿主 DSH 自身提供 `packages/schedule`（真正的 cron 语义），且 `.agents/skills/` 正是它加载技能的约定目录。

也就是说，"常驻服务"要自己造的东西，绝大多数已经存在且经过验证。

## Decision

流水线实现为一套 Skills（每个阶段一个携带硬规则的 `SKILL.md` + 做确定性工作的 `scripts/`），由 DSH 的定时任务触发，部署在云服务器的 DSH 上。不新建常驻服务。

判断类工作交给模型（读 SKILL.md 执行），确定性工作交给脚本（采集、上传、发布、去重比对）。

## Consequences

- 每个阶段天然可被任意兼容 SKILL.md 的 Agent 平台加载，不锁死在 DSH 上。
- 调度、持久化、告警的基础设施由宿主承担，但可用性也与宿主绑定。
- 阶段之间的接口必须是文件与明确的数据形状，而非进程内调用——这实际上强制了良好的解耦。
- 模型调用的成本与稳定性成为运行期主要变量，而非服务器资源。
