# ADR-0043：陈旧阈值必须按源自身的刷新周期算，`hot` 必须归一化成一种类型

## Context

2026-10-18 08:00 是 4 条 DSH 定时任务上线后的**第一个自然日**，采集层第一次在没有我
盯着的情况下自己跑完。输出是「成功」的（`ok: true`、7 源全成功、退出码 0），但里面
藏着两处缺陷——都不是崩溃，都是**静默地给出错误信息**：

```
"stale_sources": [{"source": "github", "age_minutes": 1230.9, "ok": true}]
```

以及池子里 github 条目的 `hot` 是字符串 `'40,798'`（其余六源都是 `int`）。

两处的性质不同，但同源：**第一处是系统在说错话**（把合法状态报成陈旧，且每天都说）；
**第二处是系统在存一个自己将来读不懂的东西**（同一个字段两种类型，只是还没有消费者
去读它）。ADR-0031 已经把「宁可漏报陈旧，也不误报」定为原则，本条是那条原则在
**多源**场景下的补课。

## 发现

### 一、全局陈旧阈值对长周期源是「每日必然误报」

ADR-0031 定了陈旧判据：读 `source_meta.update_time` 的**年龄**，超过 `--stale-minutes`
（默认 180 分钟）即记入 `stale_sources`。当时它是对的——因为当时看的是所有源的共同
行为。但它默认了「所有源用同一个刷新周期」。

实测各源在 DailyHotApi 里的缓存 TTL 并不相同：

| 源 | TTL |
| --- | --- |
| `toutiao` / `36kr` / `juejin` / `csdn` / `ithome` / `sspai` | 1 小时（`CACHE_TTL` 默认 3600s） |
| `github` | **24 小时** |

于是 github 的合法年龄上限是 24 小时，而判据是 3 小时：

```
2026-10-17 13:21 CST  刷新 → age ≈ 0
2026-10-17 18:00 CST  age =  4.7h  → 4.7 > 3  → 判为陈旧
2026-10-18 08:11 CST  age = 18.8h  → 18.8 > 3 → 判为陈旧
```

也就是说 github 在一个自然日里大约有 **21 小时**处于「被判陈旧」状态。而**每日必然
触发的告警会被忽略**——这正是 ADR-0006 / ADR-0021 / ADR-0031 反复要避免的「狼来了」。
一个每天都说「github 陈旧了」的简报，会让真正陈旧的那天也读起来像噪音。

### 二、`hot` 的类型不一致，且这个不一致会传染

实测七源的原始形态：

| 源 | `hot` 形态 |
| --- | --- |
| toutiao / 36kr / juejin / csdn / ithome / sspai | `int`（36kr 个别条目 `None`） |
| **github** | `str`，带千分位：`'40,798'` |

`niche_prescreen` 与 `collect()` 都把 `hot` 原样带出，于是同一个 `items[]` 里同时存在
`int` 与 `str`。**当前没有任何脚本按 `hot` 排序**（「卡匹配度 × 事件热度」由模型判断，
不是 Python 排序），所以这个坑**还没有绊到人**——如实记下这一点，不夸大成"已经在炸"。

但它是一个确定会踩的雷，且有两种踩法：

```python
sorted(items, key=lambda x: x["hot"], reverse=True)
# TypeError: '>' not supported between instances of 'str' and 'int'
```

更隐蔽的是**全部当字符串比较**：字典序会把 `'9,000' > '51,667'` 判反（`'9' > '5'`），
于是「热度排序」在没有任何报错的情况下给出一个错的顺序。

而残余风险 16 记的正是「热度轨迹 `hot_history` 被记录但没有消费者」——一旦让分拣用上
热度轨迹（"正在爬升"比"已经很高"更值得写），排序就是第一个要写的东西，也就是这个雷
第一个会炸的地方。在**入口处**归一，比等那天到了再让每个消费者各写一遍容错便宜。

### 三、修入口不够：存量轨迹里的旧格式仍被下游读到

修复 `normalize_hot` 之后实测发现，**已经落盘的 `hot_history` 里仍留着旧字符串**：

```
github hot=40798  hist=['40,798', 40798]
```

因为 `normalize_hot` 只在**写入新观测**时生效。这与 ADR-0042 的形状完全一致：那次是
「`kept_new` 的 `None` 在简报里印成 `?`」（只修了生产者，消费者仍读旧格式），本次是
「旧 `hot` 字符串留在轨迹里」。两次都指向同一条纪律——

> **修数据格式时，必须同时处理"已经在盘上的数据"，否则缺陷以"历史条目"的形态存活。**

## Decision

1. **陈旧阈值按源计算，不按全局统一值。**
   `source_stale_threshold(source, configured) = max(configured, TTL(source) × 1.5)`。
   TTL 由 `SOURCE_TTL_MINUTES` 表给出（github 1440 分钟，其余取
   `DEFAULT_SOURCE_TTL_MINUTES` 60 分钟）。

2. **系数而不是加「最大采集间隔」。** 曾经考虑过 `TTL + 最大采集间隔`（18:00 → 次日
   08:00 = 14h，于是 github 得到 38h）。那是**错的**，因为它把「缓存过期」与「没被
   重取」混为一谈：

   - 请求落在缓存有效期内 → 返回缓存，`age ≤ TTL`；
   - 请求落在缓存过期之后 → **触发重新填充** → `age ≈ 0`。

   过期后的那次请求会把数据刷新掉，**年龄不会累积到 TTL 之上**，所以一次采集时刻能
   观察到的合法最大年龄就是 TTL 本身，不需要再加采集间隔。加法还会把短周期源一起放宽
   （toutiao 从 3h 变 15h），那是**回归**。

   实测印证（github，TTL 24h）：10-17 13:21 填充 → 18:00 age=4.7h → 10-18 08:11
   age=18.8h → 次日 13:00 过期并刷新 → age≈0。观测最大值 18.8h < 24h ✓。

   系数取 **1.5**：年龄正好等于 TTL 时是**边界**，定时抖动会让它反复在陈旧/不陈旧之间
   翻转，于是告警变成噪音。这是经验值，非推导值（与 ADR-0016/0031/0037 的阈值同策略：
   先记下、后实测）。

3. **`max` 的语义是「TTL 推导值构成下限」。** 保留 `--stale-minutes` 是为了让运维能
   **放宽**判定（例如某源已知在维护，想让告警晚点响）；它**不能收紧到低于该源的刷新
   周期**——那正是本 ADR 要消除的误报。实测语义：

   ```
   github（TTL 24h，下限 2160 分钟）:  --stale-minutes 60/180/600/1440 → 阈值一律 2160
                                        --stale-minutes 3000          → 阈值 3000
   toutiao（TTL 1h，下限  90 分钟）:   --stale-minutes 60  → 阈值   90（被下限托住）
                                        --stale-minutes 180 → 阈值  180
                                        --stale-minutes 600 → 阈值  600
   ```

   即：传得比下限小**没有效果**（不是"收紧"），传得比下限大才生效（放宽）。

4. **`normalize_hot` 统一成 `int | None`**，落在归一化入口（`normalize_dailyhot` /
   `normalize_raw_toutiao` 都经它）。规则：`int` 原样；`str` 去掉千分位逗号与空白后转
   `int`；转不出来或空值 → `None`（**不抛异常**，因为一个源的格式问题不该中断整轮采集，
   与 ADR-0029「单源失败不中断」同策略）。

5. **`normalize_hot_history` 处理存量轨迹**，并在归一化**改变了**值时把原文留在
   `hot_raw`。理由：`'40,798'` 去掉逗号是同一个数，但若上游哪天给出 `'1.2万'` 这类形式，
   归一化就是一次**有损转换**，留原文以便将来回溯争议。

6. **`stale_sources` 的每条同时带上 `threshold_minutes`**，`source_meta` 的每条带上
   `stale_threshold_minutes`。这样简报能解释「为什么它算陈旧」，而不是只报一个年龄——
   **一个无法解释的阈值，在需要判断「这是真故障还是配置问题」时是没用的**。

## Consequences

- **「全局阈值」这个抽象在多源场景下是错的。** ADR-0031 的判据本身没问题，错的是把
  「源的刷新周期」当成常量。修法不是调大那个常量（调大到 38h 会让真故障也漏报），而是
  让阈值跟着源的**自身属性**走。这与 ADR-0037 的「自身基准」是同一思路：**判断一个值
  好坏，要拿它自己的历史作参照，而不是拿一个全局常数。**

- **`SOURCE_TTL_MINUTES` 是一份对 DailyHotApi 内部实现的假设。** 它来自读上游
  `CACHE_TTL` 默认值 + 实测 github 的实际刷新周期。若上游改了 TTL 或加了新源，这张表会
  过期——且过期是**静默的**（新源会退回 `DEFAULT_SOURCE_TTL_MINUTES`，可能因此误报）。
  当前缓解是 `source_meta` 里带上了 `stale_threshold_minutes`，让误报在简报里可读。
  记入残余风险。

- **归一化是「有损」的，`hot_raw` 是这条损失的记录。** 目前所有源都只丢千分位（无损），
  但接口不保证。保留 `hot_raw` 的成本是每个被改写的观测多一个字段。

- **本轮两处缺陷都在「多源」这个维度上。** ADR-0039（封面解释器 / 选题包日期 / 采集
  新增数）的缺陷在**段与段的接缝**上；ADR-0040（pull 三次 / 简报截断）也在接缝上；
  本条的缺陷在**源与源的差异**上。无人值守系统的失败模式集中在**它必须自己拿主意的
  地方**——段之间的状态传递、源之间的格式差异。这是第三次同主题，不是巧合。

- **验证方式**：阈值表与六个场景（github 真实 18.8h 不报、合法上界 23.9h 不报、真故障
  38h 报；toutiao 真实 0h 不报、真陈旧 4.2h 报；csdn 同）全部断言通过；`hot_history`
  归一化单元测试含非字典项与 `None` 边界；端到端 `--collect-only` 实测 `stale_sources`
  从 `[github]` 变为 `[]`，池内 95 条 `items` 与 196 条 `dropped` 的 `hot` **全部**是
  `int`/`None`，轨迹里旧字符串已转为 `hot_raw`。
