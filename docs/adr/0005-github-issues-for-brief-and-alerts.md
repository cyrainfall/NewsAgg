# 简报与告警统一走 GitHub Issue，接受「拉」而非「推」的残余风险

## Context

系统需要两个对外通道：每日简报（人看系统干了什么）与熔断告警（系统出事要惊动人）。这两个通道在早期决策中曾定为邮件（Q19 选邮件发告警、Q34 选邮件发简报）。

后经重新权衡，决定改为统一走 GitHub Issue。远端仓库 `github.com/cyrainfall/NewsAgg` 为**私有仓**，因此认知资产与未发布草稿放入 issue 不构成泄露。

需要注意，本决定**覆盖了两条既有决策**（Q19、Q34 的邮件选择），并因此推翻 ADR-0001 中"邮件告警"的措辞。

## Decision

每日简报与熔断告警统一写入 GitHub Issue，不使用邮件。

## Consequences

- **已知残余风险（未被消除）**：GitHub Issue 是**拉取**通道，不是推送通道。邮件会主动通知，issue 只会在你访问时被看到。而 ADR-0001 明确规定"告警不可达等同于静默失败，而这是无人值守下最危险的失败模式"。把熔断告警放在一个需要主动查看的通道里，直接削弱了熔断机制的意义。此风险在决策时已被提出，用户选择接受。
- **运维前置依赖**：本机 `gh` CLI **未安装**，且仓库尚无任何提交。因此实现该通道需要先安装 `gh` 或改用带 token 的 API 调用，并完成首个提交。
- 简报获得两项邮件没有的能力：可评论（便于批注）、随仓库回溯（与认知资产同一历史）。
- 通道可用性现在与 GitHub 绑定。若 GitHub 不可达，简报与告警同时失效——单一通道故障即全盲。
- 缓解措施（**已采纳，针对看守告警**）：心跳看守使用 GitHub Actions 的原生邮件通知能力，仅用于"主系统整体没跑"这一类最严重故障，因此让"推"的能力不因统一通道而丧失。注意这只缓解了看守通道；**主系统自身的熔断告警仍然只有 issue 这一条拉取通道**，残余风险未消除。若熔断在真实运行中被证明会被漏看，应把同样的兜底扩展到熔断告警。
