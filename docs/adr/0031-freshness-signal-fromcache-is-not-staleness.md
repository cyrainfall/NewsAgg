# 采集层新鲜度判据：fromCache 不是陈旧信号，updateTime 才是

## Context

ADR-0029 第四条把 `fromCache` 与 `updateTime` 一并列为"信源健康信号"。采集层首次实现时，我据此把 `fromCache: true` 判定为"陈旧源"，结果**七个源全部被标为陈旧**：

```json
"stale_sources": ["toutiao","36kr","juejin","csdn","ithome","sspai","github"]
```

但同批数据的 `updateTime` 只有约 11 分钟前——数据实际上是新鲜的。

## 问题本质

`fromCache` 的语义是"**本次响应由缓存提供**"，不是"数据是旧的"。对 DailyHotApi 这类聚合服务：
- 缓存是**正常且有意设计**的行为，用于降低对上游的请求频率；
- 对本项目而言，缓存在**风控上是正面的**（拉长真实请求间隔）；
- 缓存命中与数据新鲜度**没有必然关系**——缓存内容可能刚刚刷新过。

因此把 `fromCache` 当作陈旧判据，会产生**每日必然触发的误报**，而这正是 ADR-0006 与 ADR-0021 想避免的"狼来了"效应：一个总是报警的信号，最终会被忽略，从而掩盖真正的问题。

## Decision

**新鲜度判据只用 `updateTime` 的年龄**（`age_minutes`），阈值由 `--stale-minutes` 控制（默认 180 分钟）。`fromCache` 仅作为**诊断字段**保留在 `source_meta` 中，不参与陈旧判定。

该修正已落到 `collect.py` 的 `source_age_minutes()` 与主流程。

## Consequences

- `age_minutes` 依赖上游返回**合法且可解析**的 `updateTime`。若缺失或格式变化，函数返回 `None`，该源**不计入陈旧**——这是有意的失败方向：**宁可漏报陈旧，也不误报**，因为误报会训练人忽略告警。
- 阈值 180 分钟是**经验值**，非推导值。它与采集频率（每日 2–3 次，ADR-0006）的关系需要实测确认：若两次采集间隔也可能超过 3 小时，则该阈值会把正常的"间隔期"误判为陈旧。
- 这一发现验证了 ADR-0027"先撞墙"策略的价值：**只有在真实数据上跑一次，才会暴露判据的语义错误**。设计文档里 `fromCache` 与 `updateTime` 并列时，两者的区别并不显眼。
- 更普遍的教训：把上游字段用作**告警判据**前，必须先确认该字段的语义与"告警含义"一致。ADR-0029 记录该字段时依据的是"它对健康监控有价值"这一直觉，而未核实 `fromCache` 究竟表示什么——直觉在实现时被真实数据证伪。
