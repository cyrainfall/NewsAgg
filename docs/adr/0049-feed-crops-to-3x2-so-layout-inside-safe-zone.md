# 信息流把封面裁成 3:2，排版必须活在安全区里；但阅读量的问题不在这里

## Context

用户提出假设（原话）：「我觉得阅读量没有上来还是因为 cover 不够吸引人」，
并建议改用 `google-images` 技能取真实照片。这条假设被拆成三步执行
（用户 m07503「按顺序做」）：

1. 封面排版规矩：不复述标题，可读性下限写进自检 —— 已落地，提交 `396c723`（ADR-0044 发现六、七）。
2. 照片来源：只从 CC0 / 公有领域取图，许可证入库 —— 已落地，提交 `089e1fa`（ADR-0048）。
3. 阅读量为什么低 —— **本 ADR**。

前两步修的是「封面质量」。第 3 步我先去取平台真实数据，得到的结论是：
**封面确实还有两个硬缺陷，但它们都不是阅读量低的主因。**

## 发现

### 一、信息流把 16:9 的封面裁成 3:2，左右各切掉 93px

用 Playwright 在桌面 `https://www.toutiao.com/` 信息流上遍历全部 `img` 的
`getBoundingClientRect` 与 `getComputedStyle`：

- 卡片图片槽恒为 **156×104**（宽高比 1.495），`objectFit: "cover"`。
- 图片的**自然尺寸五花八门**：1035×582、1280×720、938×619、1080×450、
  573×829、495×788、640×360 —— 平台不做统一，靠 CSS 裁。
- 另有 164×55（`object-fit: fill`，base64 内联图标）与 323×186
  （`object-fit: cover`，首屏大卡），但正文卡片只有 156×104 一种。
- 窄视口（420×900）同样只有 156×104。
- `https://m.toutiao.com/` **导航超时**（45s，`domcontentloaded` 都没触发），
  移动端站点不可探针访问；改用桌面窄视口代替。

我们的封面是 1200×675（16:9）。`object-fit: cover` 在 3:2 的槽里意味着
**居中裁切**：安全区宽 = 675 × 1.5 = **1012px**，左右各丢 **93px**（7.8%）。

逐像素统计 5 张历史封面，**全部有内容落进裁切区**：

| 封面 | 越界亮像素 / 全部亮像素 |
| --- | --- |
| 2026-10-14-gemini4-price-war | 164 / 94647 = 0.17% |
| 2026-10-17-meta-open-source-ops-cost | 406 / 84348 = 0.48% |
| 2026-10-18-ai-tool-monetization-two-gates | 276 / 58248 = 0.47% |
| 2026-10-19-deepseek-search-per-call-pricing | 222 / 55731 = 0.40% |
| 2026-10-20-codex-cursor-workflow-migration | 234 / 104609 = 0.22% |

10-14 那张最直观：可视化后能看到 **「做应用的人省钱」的「钱」字与
「做模型的人挨打」的「打」字各被切掉一半**。

根因不是「偏心」——三个布局函数的居中都是对称的。根因是
`max_w = W - margin * 2 = 1044`，**比安全区 1012 还宽**。
排版允许文字用到 1044 宽，而安全区只有 1012，所以任何一行用满宽度的文字
必然越界。数字型布局（hero 居中、短）天然安全，长句型布局
（`contrast` / `statement`）必然出事。

### 二、可读性阈值的基准选错了：320 不是最差展示尺寸，156 才是

`FEED_THUMB_W = 320` 的来由是「平台下发 640×360，2x 资源对应 320 CSS px」。
这在**首屏大卡**（323×186）上成立，但在**正文卡片**（156×104）上不成立。

1200 → 156 的缩放是 **0.154**。于是：

| 元素 | 画布字号 | 320px 下 | 156px 下 |
| --- | --- | --- | --- |
| kicker | 42px | 11.2px | **6.5px** |
| 正文行 | 174px | 46.4px | 26.8px |
| hero | 307px | 81.9px | 47.3px |

`READABLE_PX = 11.0` 的自检在 320 基准下判定 kicker 合格，而真实卡片里它
只有 6.5px——**汉字在 8px 以下基本糊成一团**。阈值本身没错，基准偏乐观约 2 倍。

### 三、曝光不是瓶颈，点击率才是；而点击率的问题在赛道

这一条是本 ADR 最重要的发现，也是**唯一能解释阅读量的那条**：

- 6 条作品合计 **展现 1782、阅读 2**，整体点击率 **0.11%**。
- `analytics works` 的渠道分布：**推荐频道 92.63%** / 个人主页 5.90% /
  其它 1.36% / 搜索 0.08%。→ **系统确实在推，只是推了没人点。**
- 曝光本身在稳定爬升：最新一篇发布 0.1 天就有 51 次展现，折合 464 次/天；
  最老一篇 139 次/天。平均每篇 356 次展现。
- 账号状态：`在头条创作的第 6 天`，粉丝 **0**，`isOriginal: false`（全部 5 篇，
  与 ADR-0013「AI 创作内容不可声明原创」的预期一致）。

然后我去查「这个平台上到底有没有人在看这类内容」。用头条站内搜索
`https://www.toutiao.com/search/?keyword=…` 实测 7 个关键词：

| 关键词 | 结果 |
| --- | --- |
| `Codex` | 全是无关内容（Home \| Codex Design、codex alimentarius 食品法典、codices 词义解释），**零相关** |
| `MCP` | 全是 MCP 认证考试 / 主控程序 / 磁罗经导航，**零相关** |
| `Cursor 编程` / `AI 编程` | 只有 CSDN / 博客园 / 教育机构导流 |
| `DeepSeek` | 有内容，评论数 1 / 10 / 50 / 1 量级 |
| `AI 赚钱` / `AI 副业` | **大量内容**（「10 个普通人用 AI 赚钱的真实案例，最高两天赚 3 万」「中国已有 7 亿人在用 AI」），评论数最高 7 |
| `程序员 失业` | 内容多且**情绪浓**（「41 岁程序员失业，存款起码 8 位数了」），**最高 22 评论** |
| `大模型 降价` | 内容多（「小米大模型降价，最高降幅达 99%，雷军发文回应」），最高 21 评论 |
| `AI 工具` | 无结果（「请尝试缩短关键词或更换关键词」） |

再回头看头条主榜（我们最主要的候选来源之一）跨 10-17 至 10-20 进池的
18 条条目：娱乐 / 社会 / 消费 6 条，其余 12 条虽与 AI 沾边，但**全是社会化叙事**
（英伟达市值蒸发、AI 抛售潮蔓延至债市、AI 抢不到 iPhone、马斯克称美债靠 AI、
吴越发声 AI 诈骗、女子用 AI 救了前夫、90 岁奶奶是 AI 重度用户、中方回应美要求
机构停用 DeepSeek……）。**真正属于「AI 与开发者工具」赛道的：0 条。**

结论：头条读者对「AI 赚钱 / 副业」「程序员失业」「大模型降价」有真实兴趣，
对「Codex / MCP / 开发工具」**几乎零供给零需求**。我们的赛道（Q6 定案：
AI 与开发者工具）在这个平台上是错位的。

## Decision

1. **排版必须活在 3:2 安全区里。** 新增 `FEED_CARD_ASPECT = 1.5`、
   `SAFE_INSET = max(0, int((W - H * FEED_CARD_ASPECT) / 2))`（1200×675 时 = 93），
   以及 `text_bounds(W) -> (left, max_w)`：`left = SAFE_INSET + margin`、
   `max_w = W - 2 * (SAFE_INSET + margin)`。三个布局函数的
   `margin = int(W * 0.065); max_w = W - margin * 2` 全部改用它。
   **1200 宽下 max_w 从 1044 收到 858（-18%）**——代价是字要变小，换来的是
   「信息流里看到的字一个都不缺」。

2. **所有居中改为安全区中线。** `layout_number` 的 hero 与 payoff、
   `layout_contrast` 的两行与中间橙色短线、`layout_statement` 的正文，
   原来都以画布中线 `W/2` 居中；现在统一以 `margin + max_w / 2` 居中。
   `draw_lines_center` 的 `W: int` 形参改为 `cx: float`——**中线是安全区中线
   不是画布中线**，这个区别必须写在签名里，否则下一个调用点会传 `W/2` 回去。

3. **新增 `safe_zone_check(img, inset, y_from, tolerance=0.001)`，逐像素检查。**
   它与 `edge_check` 是两个不同的失败：`edge_check` 查「有没有画到画布之外」，
   `safe_zone_check` 查「画在画布内、但会被平台裁掉」。
   **分母必须是亮像素（墨），不是总像素**——总像素作分母时 1200×675 的 0.2%
   阈值等于 1620 个像素，5 张旧封面全降到 0.1% 以下，检查一声不响。
   这就是 ADR-0044 发现六的同一个错误：**分母选错，检查就会变成装饰**。
   改用亮像素后，新排版 0.00%、旧产物 0.18% 起，0.1% 阈值能把两者干净分开。

4. **新增最差展示尺寸检查（156px 卡片），但只警告不判失败。**
   `FEED_CARD_W = 156`，`px_at_card = 主元素字号 × 156/1200`，低于
   `READABLE_PX` 时进 `warnings`。**不判 fatal 的理由**：能不能达标主要由
   内容决定——858px 的安全区里一行 10 个汉字最多排到 ~85px，想更大就必须把
   句子改短，那是写作阶段的选择，不是排版能修的。判成 fatal 会让「句子稍长」
   直接发不出去，代价大于收益。

5. **`READABLE_PX` 的 fatal 基准仍是 320，不改。** 若改成 156，
   `MIN_READABLE` 会从 42 升到 `ceil(11 / (156/1200))` = **85px**，
   在 858px 安全区里一行只能排 10 个字——绝大多数标题根本放不下，
   等于把排版问题变成了写作禁令。用「fatal 按 320、warning 按 156」两级，
   让系统对真实的糟糕情况发声，但不假装能靠排版解决它。

6. **本 ADR 不改赛道。** 「AI 与开发者工具」是用户 Q6 的定案，ADR-0049 只记录
   实测事实（该赛道在头条上供需双零），**不在实现层偷偷改方向**。
   要改是产品决策，需要用户明确同意。

## Consequences

- **封面会变小、变居中。** 安全区收窄 18% 后，8 条历史标题回归的 `hero_ratio`
  普遍下降：原本勉强 0.25 的掉到 0.21 / 0.157 / 0.116，会触发
  「主元素占文字区高度不足 25%」警告。这是**正确的**——它说明长句型封面
  在这个画幅里本来就撑不起来。修法是写更短的断言，不是放宽阈值。

- **旧的 5 张封面仍是越界的。** `outputs/covers/*.png` 在 `.gitignore` 里
  （`outputs/**/*.png`），不入库；已发布文章的封面在平台上改不了。
  本 ADR 不重画它们——重画仓内产物不能让平台上的封面变好，只会让仓内
  与平台更不一致。**它们是历史证据，不是待修的状态。**

- **自检从「两段」变「四段」**：溢出 / 缩略图可读性 / 3:2 安全区 /
  最差卡片尺寸。四段都在量像素或量实际字号，没有一段在回报常量。

- **赛道错位这件事没有代码能修。** 它是本 ADR 最重要的产出，但它的落点不在
  实现里。系统能做的只有两件事：① 简报里如实呈现「展现够了、点击率 0.11%」，
  让「是不是没曝光」这种误判不再靠猜；② 把「这个平台要什么」的事实记下来，
  供以后改赛道时用。**封面、照片、排版都只能影响「看到之后点不点」，
  改变不了「谁会看到」。**

- **`safe_zone_check` 会误报一种情况**：如果将来某个布局故意把装饰元素铺满
  全宽（比如一条贯穿的色带），而那一行的颜色数 > 2，它会被算成越界。
  缓解是「该行 `len(set(row)) <= 2` 即跳过」这条装饰带豁免——但它只豁免
  纯色带，渐变色带仍会误报。真遇到时应当修的是装饰带本身（改成纯色），
  不是放宽阈值。
