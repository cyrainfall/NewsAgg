# 2GB 内存约束下的 Chrome 生命周期与 OOM 防御

## Context

ADR-0009 决定在云服务器上以 Xvfb + 有头 Chrome 运行发布链路，且以有头模式规避无头特征。但该决定**未对照实际实例规格核实**。

实际核实的结果：实例为 `ecs.e-c1m1.large`（cn-shenzhen，运行中，公网 IP `120.25.146.106`），规格 **2 核 / 2GB 内存 / 40GB 系统盘（cloud_essd_entry）**。

2GB 需要同时容纳：Chrome（有头，单个渲染进程通常数百 MB 至 1GB）、Xvfb、DSH 宿主、mihomo 内核（ADR-0022）、以及 git 操作。**OOM 是大概率事件而非边缘情况。**

这一点特别危险，因为它的表现是"发布阶段莫名失败"——最难归因的一类故障，且发生在唯一不可逆的环节。

## Decision

**保持 2GB 实例**（不升级），通过以下三层防御应对：

**一、Chrome 按需启动，用完即杀。** 不在内存中常驻。发布与数据读回完成后立即终止 Chrome 进程。
这是 2GB 下最有效的单一措施：Chrome 只在几分钟的发布窗口内存在，其余时间内存全归 DSH 与 mihomo。

**二、内存约束参数。** 启动 Chrome 时施加：

| 参数 | 作用 |
|---|---|
| `--disable-dev-shm-usage` | 避免 `/dev/shm` 不足（小内存与容器环境常见坑） |
| `--renderer-process-limit=1` | 限制渲染进程数，避免进程级内存碎片 |
| `--js-flags="--max-old-space-size=..."` | 限制 V8 堆上限，防止单个页面无限增长 |
| `--disable-gpu` | 服务器无 GPU，禁用可省内存 |
| `--no-sandbox` | 服务器环境必需 |

**明确不使用 `--single-process`。** 它破坏 Chromium 的进程隔离模型，以不稳定与随机崩溃著称——那等于**把 OOM 换成更难归因的崩溃**。在发布这一不可逆环节，崩溃比 OOM 更糟：它可能停在填了一半的表单上，从而进入 ADR-0011 的"结果未知"路径。

**三、2GB swap 兜底 + 发布前内存预检。** 发布前检查可用内存，不足则告警且**不启动** Chrome（宁可当日熔断，也不在内存紧张时进入不可逆流程）。

## Consequences

- **发布前内存预检是新增的一道门**，它属于 ADR-0013/0020 的安全门体系，但性质不同：前几道门校验内容与表单，这道门校验**运行环境是否具备执行条件**。
- swap 建在 `cloud_essd_entry` 上，性能有限。因此 swap 只应作为**避免 OOM kill 的兜底**，不应被视为可用内存：一旦发生实际换页，Chrome 操作会显著变慢，而发布超时会走 ADR-0011 的路径（先核实后台列表，不确定则熔断）。也就是说 swap 把"崩溃"转换成了"可能超时"，这是有意的取舍但不是免费的。
- 保留 2GB 意味着**整个系统长期运行在内存紧张状态**。若未来出现以下任一情况，应重新评估升级：新增常驻服务、Chrome 之外再引入浏览器实例（如为第二阶段的小红书准备）、或 OOM 在实际运行中真实发生。
- 按需启动使 Chrome 的**启动可靠性**成为发布链路的关键依赖：每次发布都要冷启动一次 Chrome 并加载已持久化的 profile，启动失败即当日熔断。因此 Chrome 启动脚本需要独立可测。
- 本 ADR 修正了 ADR-0009 的一个疏漏：该 ADR 论证了"为什么有头而非无头"，但未核实实例是否有足够内存承载有头 Chrome 的额外开销。
