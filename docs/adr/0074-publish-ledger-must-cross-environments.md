# 发布账本要跨环境可用：运行时账本 + 入库归档

## Context

2026-10-27 在服务器上跑表现数据回路，发现一个只有跨环境才暴露的缺陷：

```
本机   from_ledger: 12  → 11 篇全部匹配
服务器 from_ledger: 0   → 11 篇只匹配 9 篇
```

服务器上 `unmatched` 的两篇是：

- 《老板叫停AI裁员，中间层位已经换成外包》（gid 7699135881185149480）
- 《模型打五折，未必是好事》（gid 7696532785528160795）

数据在，关联断了。

### 断在哪

`local_title_index()` 用两条路把平台作品关联回本地成稿：**gid** 与
**标题**。标题这条路有两条补充来源——账本里的 `title`（成稿标题）与
`title_on_platform`（平台实际收到的标题）。服务器上账本是空的，于是只剩
`outputs/*.md` 一条路，而那两篇正好都匹配不上：

1. **改稿后标题漂移**。`outputs/2026-10-14-gemini4-price-war.md` 现在的 H1
   是「Gemini 4 打五折：做应用的人在省钱，做模型的人在挨打」，而发布当时的
   标题是「模型打五折，未必是好事」。改稿是 ADR-0026 循环 B 的改稿飞轮做的
   （提交 `5139bc8`）——**这是设计**，不是错。平台上永远是旧标题。
2. **输入框吞字**。头条的标题输入框会吞字（ADR-0051，2026-10-21「中间层
   岗位」→「中间层位」）。账本里的 `title_on_platform` 才是平台真正收到的
   标题，`outputs/` 里没有这个信息。

两条路都指向同一个事实：**账本里有成稿里没有的信息**。

### 为什么账本此前不入库

ADR-0027 决策四：「本地与服务器各自持有运行时状态」，`.gitignore:48`
排除整个 `.newsagg/`。当时的理由是「运行时状态不入库以免两边冲突」——
那条理由在「双环境同时跑、各自独立」时成立，在「主环境从本地迁到服务器」
时不成立。

更早的 ADR-0036 Consequences 已经写明：「账本一旦丢失（换机、清空运行时、
服务器重建），快照就退回路径 2 的时序假设……**不要把账本当可重建的缓存**」。
ADR-0055 也写「`.newsagg/publish-ledger.jsonl` 值得单独备份——但当前没有做」。
**这条风险记了两个月，落地时才第一次真的发生。**

## Decision

**账本分两份：运行时账本（不入库）+ 入库归档（跨环境的合并视图）。**

### 一、运行时账本仍是第一手事实

`.newsagg/publish-ledger.jsonl` 保持不动，仍是当前环境刚写出来的记录。
发布层照旧只写它。理由：它是**运行时状态**——锁、熔断、候选那些东西同样
不入库，账本跟它们在一起才不显得特殊。

### 二、归档进 `reports/`

`reports/publish-ledger.jsonl` 是入库的合并视图。选 `reports/` 的理由：

- ADR-0012 里 `reports/` 的语义就是「冻结成结论的产物」，本来入库
  （已有 13 份简报 + `reports/performance.jsonl`）；
- `reports/` 没有任何 glob 遍历（只有 `performance.py:505` 与
  `brief.py:165,293` 的说明文字），加一个文件不会破坏任何现有逻辑；
- 「某天发了什么」本来就是简报要讲的事，归档与简报同目录说得通。

### 三、合并规则

读者一律读**合并视图**，不自己读文件——ADR-0042 记过「三份 frontmatter
解析器漂移」，这里不会再造第四份账本解析器。

去重键 `record_id`：

- 优先用记录自带的 `record_id`（发布时写入）；
- 旧记录没有，用 `at|slug|mode` 派生。派生键在两台机器上算出来一样——
  `at` 是 ISO 时间戳、`slug` 是文件名、`mode` 是发布方式，都是内容决定的。

同一 id 的两份记录比新鲜度（`updated_at`，没有则 `at`）：

- **大的胜**——「本地标了 `deleted_at`」这类修订会同步进归档；
- **平手时运行时胜**——当前环境刚写的版本是新鲜的；
- **归档独有的记录永远保留**——另一个环境发过的文章不该被本地账本抹掉。

### 四、归档入库前必须过凭证扫描

归档要入库了，所以扫描分两层：

- **键名层**（递归）：`sessionid` / `cookie` / `token` / `password` /
  `secret` / `authorization` / `uid_tt` / `sid_ucp` / `ttwid` / `odin_tt`
  等，命中即**跳过整条记录**；
- **值层**：`msToken=` / `a_bogus=` / `sessionid=` / `sid_ucp_v1=` /
  `Authorization:` 这类「参数名=值」形态。

命中就跳过并计数，**不是报错**——发布已经成功了，账本写不进去不该让发布
失败（ADR-0006）。

扫描刻意**不做全文关键字匹配**：账本里出现过一次误报（`correction_note`
的叙述文字提到 `page.keyboard.type`），全文匹配会把那种记录误杀，而误杀的
代价是账本说谎。叙述文字里提到一个词不等于那是一个凭证。

### 五、四个读者统一走合并视图

`style_learn.py`（找发布快照）、`triage.py`（slug→观点卡映射）、
`performance.py`（作品关联）、`brief.py`（今天发了什么 / 误发 / 微头条泄漏）
——全部改用 `.agents/lib/publish_ledger.py` 的 `read_merged(root)`。

`brief.py` 的 `section_actions` 新增可选参数 `all_recs`：调用方传已经算好的
合并结果，不传则回落到只读 `ledger_path`（旧调用方与测试的兼容路径）。

## 实测

| 场景 | 结果 |
|---|---|
| 本机 `sync_archive()` | 运行时 12 条 + 归档 0 条 → 合并 12 条 → 写入 12 条，0 条被凭证扫描跳过 |
| 本机 `performance.py --dry-run --backend api` | `on_platform 11 / matched 11`、`unmatched []`（与改动前一致） |
| **模拟服务器**（复制 `.agents`+`outputs`+`reports`，删掉运行时账本） | `read_merged` 读到 12 条（**改动前是 0 条**） |
| **模拟服务器**跑 `performance.py --dry-run --backend api` | `on_platform 11 / matched 11`、`unmatched []`——**断链修好了** |
| 派生键唯一性 | 12 条记录 12 个不同 id（10-24 那篇有两条：正常发 + 误发，`at` 不同） |
| 凭证扫描 | 嵌套键（`{"nested": {"ttwid": …}}`）也能抓到——第一版只扫顶层键，测试抓出来了 |
| 全量测试 | `Ran 149 tests OK (skipped=14)` |

## Consequences

- **服务器上有了账本。** 表现回路的作品关联恢复；风格回路的发布快照基线
  恢复（`snapshot.git_blob` 在归档里）；分拣的 slug→卡映射恢复；简报能报
  出另一个环境发的文章与遗留的误发/泄漏。
- **归档是公开仓库里的文件。** 账本里记着标题、gid、卡文件名、发布时间、
  收益快照的引用——这些都不是凭证，但**账号的发布历史从此是公开的**。
  这是有意的：仓库本来公开，文章本来公开，账本只是把它们关联起来。
- **凭证扫描是兜底不是保证。** 它按键名与参数名形态扫，新增的凭证形态
  可能扫不到。真正的保障是**账本里本来就不该有凭证**——发布层写的是
  标题、gid、快照指纹、错误摘要。
- **合并规则有一个未覆盖的场景**：两个环境**同时**给同一条记录做不同修订
  （本地标 `deleted_at`、服务器标 `leak_accepted_at`），平手时运行时胜会
  丢掉其中一边。现实里不会发生（同一账号只有一个人操作），但如果哪天
  有了，它会以「某个提醒不再出现」的形式表现。
- **`sync_archive()` 在编排的第⑦⑧步、出简报之前跑。** 顺序有意义：简报
  读的「今天发了什么」来自合并视图，归档必须在简报之前落好。归档写失败
  不阻塞本轮运行（`--no-git` 时直接跳过）。
- **服务器要成为主环境，还需要解决 git 推送凭证**（实测
  `git push --dry-run origin main` → `could not read Username for
  'https://github.com'`）。归档是入库产物——**推不上去，跨环境就还是断的**。
  这一条不在本 ADR 的范围内，但它是「归档」这个决定能否兑现的前提。
