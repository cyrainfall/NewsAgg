# 无人值守自动发布，接受账号风控风险

## Context

系统目标是"自动化收集→提炼→输出→发布"。发布侧要求无人值守，即定时任务自动把文章发到今日头条，无需人工确认。

此决定经一次专门调研后**被重新确认**（而非未经审视地维持）。调研得到的、使这个决定代价明确的事实：

1. **官方无文章发布 API。** 字节开放平台的[头条内容发布接入方案](https://open.douyin.com/platform/resource/docs/ability/content-management/toutiao-publish-solution/) 明文写明"仅支持小视频格式，暂不支持发布头条文章、微头条等"。唯一官方自动化发文章通道「内容源接入」仅限**新闻媒体与国家机构**账号。个人/企业头条号的文章发布**实际上只有 Web UI 一条路**。
2. **浏览器自动化被用户协议明文禁止。** [头条号用户协议](https://www.cnsoftwarelaw.com/contract/2020/0215/142.html) §4.1.1 禁止使用未经授权的"插件、外挂、系统或第三方工具"。这不是"可能受限"，而是**构造上即违反协议**。
3. **AI 内容不能声明原创。** [文章原创规则](https://baike.toutiao.com/detail/242/243/0) 明确把"AI创作内容"列为不可声明原创，因此本流水线的产出同时丧失原创与头条首发（2× 补贴）。
4. **平台正在大规模治理同类内容。** 头条 2025 治理白皮书称处置低质 AIGC 内容 **260 万+ 条、处置账号 1.1 万+**。
5. **反自动化是多层的。** 后台有 argus 指纹风控（裸 Python 被拦截、伪装 Chrome 的客户端可通过），外加设备指纹、IP 段、发布节奏规律性检测。信用分从 100 起扣，**归零即永久封禁**。

同时，此决定与本工作区既有资产的安全约束冲突：`xiaohongshu-skills` 的 README 警告高频自动化会导致账号受限，其 `xhs-publish` 技能把"发布前必须让用户确认最终标题、正文和图片"写成必做约束；`wewrite` 的状态契约默认 `permissions.publish: false` 且规定"只有用户明确要求发布才为 true"。

换言之：本决定**主动推翻了两套复用技能的既有安全约束与一份调研的相反建议**，把账号（整条流水线唯一不可替换的资产）暴露在封禁的尾部风险之下，以换取"无需人在场"。

## Decision

采用无人值守自动发布。发布层长期持有凭证（接管已登录的真实浏览器，而非存储账号密码），并由熔断机制兜底：遇到登录失效、发布被拒或内容被限流时，停止自动发布并告警等待人工介入，不做自动重试——在风控对抗场景下重试会放大损害。

发布内容**主动标识 AI 生成**，且**绝不声明原创或头条首发**。这不是合规上的让步，而是避免命中"以 AI 内容冒充人类创作"这一明确违规项的必需条件。目标为获得关注，而非创作分成，故放弃原创资格是可承受的代价。

## Consequences

- 发布层不能是一次性脚本，必须是一个能长期持有会话、检测自身失效并主动告警的组件。
- 熔断告警通道成为流水线的关键路径依赖：告警不可达等同于静默失败，而这在无人值守下是最危险的失败模式。告警渠道的选择见 ADR-0005，其中包含一个**已知且未被消除的残余风险**。
- 内容侧的去重（取舍判定）从"省算力"升级为风控措施：社区规范明确禁止"批量发布重复内容/高度相似内容"，重复发文会直接推高账号风险。
- 发布必须走真实浏览器会话语境（argus 会拦裸 HTTP 客户端）并采用拟人节奏，不能使用固定间隔的机械调度。
- 流传的"安全频率"数字（微头条 10/日、文章 5/日等）**均无官方来源，不得作为架构依据**；应保守取低于传闻的值。
- 文章封面图为必填项（单图/三图），因此配图是发布链路的硬依赖，不是可选增强。
- 若账号最终受限，损失不可通过技术手段回滚。此风险已被明确知悉并接受，且已知悉其性质是"违反平台协议"而非"可能被误判"。
