# 正文里又带了一遍标题：两条写路径读了两个不同的输入

## Context

2026-10-30 21:06 的文章发布后，用户发来手机截图：标题出现了两遍——标题栏一遍，
正文开头一遍（带平台的红色引用条）。当天这篇的 `verdict` 是 `title_found`，
反查通过，账本正常，测试全绿。

## 发现

### 一、浏览器写路径把整份 `.md` 交给了平台

`publish.py` 里的 `read_publish_snapshot()` 早就把标题与正文分开了：

```python
m = re.match(r"^#\s+(.+)$", text, re.M)
if m:
    title = m.group(1).strip()
    body = text[m.end():].lstrip("\n")
```

api 写路径用的是这个 strip 后的 `body`（`_api_write(..., body=body)`）。
但浏览器写路径——**也就是生产路径**（ADR-0073 记过：写路径不给 api；ADR-0080 又
记了本机 api 后端因 cookie 权限闸根本走不通）——是这样调的：

```python
"--content-file", str(root / "outputs" / f"{args.slug}.md"),
```

交的是**原文件**。而 `outputs/<slug>.md` 的第一行按写作要求就是 `# 标题`（首行一级
标题 2~30 字）。平台把标题当独立字段渲染在标题栏，正文里那行 H1 于是成了标题的
第二遍。

同一个语义，两个输入源。api 那份 strip 了，browser 这份没有，而只有 browser 在生产
上跑。

### 二、它连带让「标签算的正文」不是「平台收到的正文」

`prose_tags = pr.tag_body(body, ...)` 用的是 strip 后的 `body`（第 800 行拿到的那份），
和 api 路径一致。所以次日简报③段印的「收尾 / 反转句 / 先例段」四个标签，是在**一份
平台上并不存在的正文**上算出来的——少了一行 H1，其余相同，对标签结论没有实际影响，
但这条事实本身值得记：**只要两处输入源不同，「验过的」与「发出去的」就不是同一个
东西**。

### 三、为什么三个验证都没拦住

| 验证 | 结果 | 为什么拦不住 |
| --- | --- | --- |
| 单元测试 260 个 | 全绿 | 没有任何测试检查「交给平台的文件长什么样」 |
| 反查 `title_found` | 通过 | 它查的是**标题栏**，标题当然在；查的不是正文 |
| 账本 / 退出码 | 正常 | 平台不认为这是错误：正文里多一行标题是合法内容 |

于是缺陷的形状是：**退出码 0、verdict 正确、测试全绿，而读者看到的是重复标题。**
这是本项目第五次撞到同一类形状（ADR-0042/0043/0054/0057/0081）——**被验证的东西
和用户看见的东西不是同一处**。

波及范围：账本里明确记着 `write_backend: browser` 的 4 篇全都带这个问题；更早 11 篇
的真发记录没有这个字段（字段是后加的），但代码路径是同一份，**大概率从浏览器成为
唯一写路径那天起就一直在发生**。用户是在手机上第一次注意到的。

## 决定

1. **在发布层修，不动 vendored 的 toutiao-ops。** 新增 `write_body_file(root, slug, body)`：
   把 strip 后的正文写进 `.newsagg/tmp/publish-<slug>-body.md`，浏览器路径改传这个文件。
   放 `.newsagg/tmp/` 而不是 `tempfile`：路径固定，事后能直接打开核对这一次到底交了
   什么给平台。
2. **让两条写路径共用同一份正文。** 修完之后 `prose_tags`、api 的 `body`、browser 的
   `--content-file` 三者是同一份字节。
3. **补两个测试**：一个功能测试（正文文件不含标题行、逐字节等于 strip 后的 body、
   落在 `.newsagg/tmp`），一个**源码级断言**（浏览器路径必须用 `write_body_file`，
   且不能再出现 `--content-file outputs/<slug>.md`）。后者钉的是「线有没有接上」——
   这个缺陷功能测试全绿，只有源码断言能在它复发时先红。

## 未做

- **今天这篇的正文仍有重复标题**：已经发出去了，改它要走平台后台编辑，属于人的动作，
  不由 agent 自动做（与「发布绝不自动重试」同一条纪律：平台上的写操作不自动化到第二遍）。
  简报⑤段已写明「在后台删掉正文第一行」。
- **历史文章不回溯修正**：11 篇以上都带着这一行。修正它们的收益是排版，成本是每篇
  一次平台编辑动作，而文章已经分发过。留在原地比批量改更安全。
- **没有加「正文首行不得是标题」的发布前校验**：修在输入源上比加校验更根本——校验只能
  发现症状，而这次的根因是「两个输入源」，校验反而会变成第三个需要维护的地方。
