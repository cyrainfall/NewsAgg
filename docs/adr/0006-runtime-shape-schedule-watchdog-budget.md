# 流水线的运行形态：技能分层、调度、看守与预算

## Context

系统需在云服务器上无人值守运行。经过多轮决策，落定了四条相互关联的运行约束，它们共同决定了架构形状，因此记录在一起。

## Decision

**一、技能分层与模型选型。** 分拣层每日需全量读取全部观点卡正文（这是取准"接得上/接不上"与"有无新进展"的必要代价），成本随卡库线性增长，故分拣使用**便宜快模型**；写作层产出决定用户是否愿意署名，故使用**强模型**。wewrite 官方支持以 `WEWRITE_WRITER_API_KEY` 单独路由写作模型，因此这一分层不需要自建路由。

**二、调度。** 采集每日 2–3 次（捕捉事件发酵过程，同时降低单次请求频率以对风控友好）；当晚发布（平台流量高峰前）；次日下发简报。

**三、看守。** 主系统的故障（登录失效、发布被拒、限流）由熔断捕获，但**主系统完全没跑**这一类故障它自己永远发现不了——而"今天没有值得写的选题"是合法结果（允许弃权），两者从外部不可区分。因此增设一个**独立看守**：一个 GitHub Action 定时检查"今天应有的简报 issue 是否存在"，缺失即通过 **GitHub Actions 原生邮件通知**推送（这是全系统唯一的推送通道，见 ADR-0005）。它运行在不同机器、由不同调度器触发，因此能发现主系统整体失效。

由此推出一条硬性要求：**每日简报必须无条件存在**，包括弃权日。若有选题就报告进展，无选题就显式声明"今日弃权"。简报的存在本身就是心跳；缺了它，看守会误报，而误报会让看守失去可信度。

**四、预算。** 设每日费用上限（$5 量级）。超限则降级为"只跑分拣不写稿"并告警，而非静默继续或整体失败。

## Consequences

- 分拣层的成本随观点卡库增长而单向上行。这是一个已知的、随资产积累而加剧的压力点；若卡库增长到分拣预算无法承受，需要引入候选召回（先粗筛再精读），但那是优化，不是当下的问题。
- 看守依赖 GitHub Actions 与私有仓，因此"仓库可访问"成为系统可靠性的隐含前提；若仓库或 Actions 失效，看守与简报通道同时失效。
- 采样的时间分布（每日 2–3 次）意味着两次采集之间发生并迅速消退的事件可能被漏掉。这是为降低风控风险而付出的信息代价，已被接受。
- 预算降级路径本身需要被测试：一条"降级后不再写稿"的路径若从未触发过，其正确性就只是假设。
