# 单篇数据接口的 type 参数传错了，接口一直是好的

## Context

2026-10-26 用户要求「查如何提高点击率」（m21678）→「诊断」（m21753）→「要」（把结论落成标题规则，m21829）。诊断过程中需要拿到后台「查看数据」弹层里的三个指标——**阅读完成率、平均阅读时长、点击率超过同类作品百分之几**——因为公开调研给出的达标线是「点击率 ≥10%、完成率 >40%、停留 >60 秒」，而我们只看得到展现和阅读（ADR-0037 判定 `content-detail` 不可用，于是循环 C 改用 `content list` 的 `itemCounter`）。

探查时先做了两件直觉上该做的事：读后台弹层的 DOM、抓网络请求。抓包结果直接给出了答案——**弹层的数据来自一个我们一直判定为「不可用」的接口**：

```
GET https://mp.toutiao.com/mp/agw/statistic/v2/item/info?item_id=<gid>&type=1&app_id=1231
```

`type=1`。而我们调的时候是 `type=2`。

## Decision

**一、`analytics content-detail` 的默认 `--content-type` 从 2 改为 1。**

平台自己的类型枚举（从 `@mp/analysis` 前端包里抓到的原文）：

```js
{All:0, PgcArticle:1, Video:2, Weitoutiao:3, Wenda:4, ShortVideo:5, Audio:6, PgcGallery:7, Invalid:8}
```

**图文文章是 1。** 原先的默认值 2 是 `Video`。vendored CLI 里的注释「2=图文/微头条, 3=视频」**从来就是错的**——按那个注释理解成「2 覆盖图文」，于是所有文章都用了视频的类型号。

**二、1003 ��再是一个二义的成功响应，显式区分两种含义。**

传错 type 时接口不报参数错误，只返回：

```json
{"code":1003,"item_data":{},"message":"数据开小差啦~请稍后再试"}
```

而「这个作品确实没有数据」返回的**是同一个形状**。`getContentDetail` 现在按 type 是否在枚举内分流：

- type 不在 `0..7` → `success:false` + `error: "content-type 编号 X 不在平台枚举 0/1/2/3/4/5/6/7 内，接口因此返回 1003（不是「没有数据」）"`
- type 合法但 1003 → `success:true, noData:true, note: "平台返回 1003：type 合法，但该作品暂无数据（通常是发布次日 14:00 前数据未就绪）"`

**三、修正 ADR-0037 与 ADR-0024 的错误陈述。**

ADR-0037 第二条写的是「上游 API 返回空数据，不可用」；ADR-0024 的能力表把 `analytics works` / `content-detail` 标成「接口存在但数据不可用」。这两处现在都不成立。ADR-0037 的**结论**（循环 C 的唯一数据源是 `content list`）仍然成立——`content list` 确实一次拿到全部 10 篇的展现与阅读，比逐篇调 `content-detail` 便宜得多；变的是**「`content-detail` 不可用」这个事实判断**，以及由此关掉的那条能力路。

## 这次错法的形状

值得单独记一笔的是**这个错是怎么变成一条被写进 ADR 的结论的**：

1. 探测时用了默认值，默认值是错的（2 而不是 1）；
2. 接口对错参数和「无数据」返回**完全相同**的响应；
3. 于是「1003」被读成「这个接口坏了」；
4. 那个读法被写进 ADR-0037，还在 ADR-0024 的能力表里标成 ⚠️；
5. 半年内没有人再试过这个接口——因为「已确认不可用」比「未确认可用」更省事。

ADR-0037 自己的 Consequences 里其实写着警告：「**能力表是『接口存在』的证据，不是『数据可用』的证据**」——但它自己就是这句话的第一个受害者。写下了教训的文档，紧接着犯了那个教训。

**一条具体的、可执行的检查**（这次真的能防住）：**凡是把接口判为「不可用」的结论，都必须附一次「参数全枚举」的证据**。一个接口只有一个参数错了就足以产出 1003 这种无信息响应时，「试了默认参数」根本不构成探测。这一条已写进本 ADR，因为它下次还会遇到。

## 口径备忘（避免下次再猜）

- `-1` = 数据未就绪。平台规则：**作品发布次日 14:00 后数据才可查**（`/mp/agw/statistic/v2/helper/latest_ready_date` 返回 `{"code":1200,"impression_latest_ready_date":"2026-10-25"}`）。当天新发的文章必然是 -1，**不是 0**。
- `0` = 数据已就绪但确实是 0。0 阅读的文章完读率就是 0，不是缺失。
- `ranking_data.click_rate_rank` 的值**就是**后台文案里的「超过 N% 同类作品」的 N。实测 10-20 那篇 API 给 `click_rate_rank: 2`，后台写「点击率 1.0% 超过 2% 同类作品」，对得上。
- `consume_detail` 三兄弟：`click_rate`（小数，0.0123 = 1.23%）、`read_complete_rate`（百分数，30.86 = 30.86%）、`read_duration`（秒，50 = 50 秒）。

## Consequences

- **单篇表现数据现在可以按需拉取**，不再受限于 `content list` 的两个计数器。ADR-0037 记的「读不到完读率/停留时长/同类百分位」这个缺口关闭。
- **但 `content list` 仍是循环 C 的默认数据源**，本 ADR 不改这个决定。理由：`content list` 一次拿全部 10 篇，`content-detail` 要逐篇调用；两者的展现/阅读口径一致（实测 `content list` 的 `showCount` 1290 与 `item/info` 的 `impression_count` 1290 相同），所以 `content-detail` 用来**补那三个 `content list` 没有的指标**，不用来替换。
- **调用成本变了。** 每次 `content-detail` 都要起一次浏览器会话（ADR-0030 的串行锁约束照旧）。要拿 10 篇的完读率意味着 10 次调用，或者一次会话里循环调同一个接口——后者需要一个新脚本。
- **这次修的是 vendored 的第三方代码**（`reference/toutiao-ops/`）。按 ADR-0018，它属于「不入库」的那一类，但本仓已 vendor 了 `reference/toutiao-ops/`（`.gitignore` 有 `!reference/toutiao-ops/` 例外），所以这个修改会随仓入库。上游原仓库仍有同样的 bug，升级时需重新核对本段。
- **ADR-0037 与 ADR-0024 已被本 ADR 推翻的部分以勘误块标注**，不删除原文——原文记录的是当时的判断，勘误记录的是判断的修正，两条都要能查到。
