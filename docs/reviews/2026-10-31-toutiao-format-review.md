# 复盘：头条热榜的格式基线（2026-10-31）

## 起因

用户要求：「自己去浏览头条热榜，学习热门的头条是怎么样的，包括配图、标题、正文等内容，
你要学会自进化（Self-evolving／RSI）」。

「学会」这件事在这个仓库里的含义是固定的（ADR-0007/0018/0069）：**不是写一篇感想，
是把观测变成可复查的数字，再把数字变成下次运行时真的会生效的约束。** 所以这次没有从
「我觉得头条喜欢短标题」开始，而是先造一把尺子。

## 做法

1. **造尺子**：`scripts/style_probe.py`（stdlib，无第三方依赖）。同一组指标同时量平台
   文章与我们自己的成稿——标题字数、正文字数、段数、段均、最长段、首段字数、小标题数、
   数字密度（每百字）、引号密度（每千字）、第一人称密度、内文图数。
2. **取样本**：热榜话题 50 条（本地 DailyHotApi，与采集层同源）；正文 7 篇
   （`m.toutiao.com/i<id>/` 移动页是服务端渲染，PC 页和 `web_fetch` 都只拿到 JS 壳）；
   热榜前 10 条封面逐张看过。
3. **同口径量自己**：`outputs/*.md` 全 15 篇。
4. **存档**：`.newsagg/platform-samples/2026-10-31.json`，含本次用了哪几个 id。

## 测量先纠正了三处「尺子错」

这三处如果没抓出来，后面所有结论都是错的——它们与 ADR-0081（阅读率算出 120%）
是同一类缺陷：**数据本身没错，是量法错了，而错的东西会被印出来当成事实。**

| 错误 | 表现 | 原因 |
| --- | --- | --- |
| 首段字数 | 平台中位 13 字，像「平台开头极短」 | 把「图片来源：unsplash」「发布会现场」这类**图注**当成了首段 |
| 引号密度 | 我们全 15 篇 = 0.0，像「从不引用原话」 | 只数了弯引号 `“”`，而我们全篇用直角引号 `「」` |
| 内文图 | 平台 0 张，像「平台也不配图」 | 只认 `src`，而头条正文图是懒加载（`src` 是占位 gif，真地址在 `data-src`） |

修完三处才拿到第一份可用数字。**这一步比任何结论都重要**：本次两次被推翻的判断，
都是因为先信了没修过的数。

## 测量又推翻了我两个判断

### 一、「我们的标题太长」——错

第一版我只看了 50 条热榜话题：字数 8–20、中位 15，而我们 27 字。看起来是铁证。

但热榜上的那 50 条是**话题名**（「黄金大跌 铜价为何创新高」），不是**文章标题**。
量了 7 篇真文章的标题后：17–53 字，**中位 31**，我们 27 反而偏短。

教训：**「热榜话题」和「文章标题」是两种东西，不能拿前者的长度去砍后者。**
这条已经写进 `platforms/toutiao-format.md`，防止下一个人（包括我）重犯。

### 二、「我们的段落太碎、最长段太短」——错

n=3 时算出：平台最长段 334 字、我们 183 字，差距 151 字，看着像"我们不敢写长段"。
n=7 后：平台 151、我们 183，我们反而更长；段均 95 vs 101，同一量级。

教训：**n=3 的结论不要写进规则。** 样本从 3 扩到 7，两处结论直接翻转，另有一处
（字数差）从 +218 放大到 +839——**样本量不足时，差距会被系统性低估**。

## 稳定成立的四条，与已落地的改动

两次不同 n 都一致的四条差距：

1. **篇幅偏长 +839 字**（我们 2343，平台 1504）
2. **小标题过多**（我们 5 个，平台 7 篇里 6 篇为 0）
3. **首段过长**（我们 97 字，平台 38 字）
4. **没有内文图**（我们 0，平台中位 2）

前三条是文字约束，已经改进**每天生成任务书的地方**（`build_brief.py` 第 20–23 条），
所以从明天那一篇起就生效，不需要谁记得：

- 第 20 条：首段 ≤ 60 字，只放一句判断（背景挪到第二段）
- 第 21 条：小标题 0–2 个（仍写就按第 7 条写成读者利益句）
- 第 22 条：篇幅往短端写（平台 1504，我们 2343）
- 第 23 条：**禁止写「如图」「见下图」**——我们没有正文插图能力，写了就是空指

第四条是**能力缺口**，不是写作规则能解决的：`fetch_photo.py` 只服务于封面，
vendor 的 toutiao-ops 没有正文插图接口。要做需要「选图（相关性 + 版权）」与
「编辑器上传」两件新东西，已记入 `platforms/toutiao-format.md`，没有写进任务书
（不要求做不到的事）。

## 为什么这算一个回路，不是一次性读后感

| 环节 | 落点 |
| --- | --- |
| 观测 | `scripts/style_probe.py`（同一把尺子量两边） |
| 证据 | `.newsagg/platform-samples/<日期>.json`（含 id 与日期，可复查） |
| 事实 | `platforms/toutiao-format.md`（带样本量的基线表 + 已知缺口） |
| 约束 | `build_brief.py` 20–23（明天生成任务书时生效） |
| 复测 | 同一脚本重跑；样本变了结论会变，本次已变过一次 |

关键是第 5 行：**尺子和样本都留下来了，下次不用重新发明。** 这与 ADR-0069 的做法一致
（规则一份文件、实现一处、消费者多处），区别只是这次的消费者是「下一轮的任务书」。

## 未做（明确留给后续）

1. **把「首段字数」「小标题数」变成发布标签**，让简报③段每天自动印出「本篇 vs 平台基线」。
   现在只有 `prose_rules.py` 的四个标签（收尾方式/反转句来源/先例段/引自己上一篇），
   格式类指标还没进账本。做了之后，这个回路就**不再依赖有人主动跑 probe**。
2. **正文插图能力**（见上）。
3. **每周复采**：现在样本是手工触发的。理想形态是定时跑 probe 刷新基线；但这要新增一条
   定时任务，而本机的 4 条任务是按 ADR-0079 仔细定过的，加第五条应该是一次明确的决定，
   不该由我在夜里顺手加。
4. **封面 A/B**：平台热图几乎都带真人或实景，我们是纯文字模板。但**没有对照数据**，
   拿不到「同标题不同封面」的效果差异，所以本次不动封面，只记录。

## 诚实边界

- **看不到阅读量**。这 7 篇文章我不知道爆没爆，只知道它们出现在头条的搜索结果与热榜附近。
  所以本文只能说「平台上长这样」，**不能说「这样才会爆」**。后者需要曝光数据，本系统没有。
- n=7，非随机抽样（按赛道挑的）。
- 我们自己只有 15 篇、阅读率 0.0x%，**任何"改了就更好"的话都是假设**，只能靠后续数据检验。
- 三条已落地的约束（首段/小标题/篇幅）同样只是假设。它们的检验方式不是"我觉得更顺"，
  而是明天那篇的阅读率与完读率——而这两个数在 0.0x% 的样本量下，暂时什么都证明不了。
