# 修改与删除：把「只能人工去后台」变成两条带闸的命令

## Context

用户要求补全头条 CLI 的**修改**和**删除**操作。

这件事此前被三次判过死刑，但判的理由各不相同：

- **ADR-0017**：系统**不自动**编辑或删除已发布内容。理由是「自动删改是高风控信号」，
  且「自动改正」在无人校验时可能越改越糟。
- **ADR-0047 / ADR-0055**：`toutiao-ops` 的 `content-manage.js` 只导出 `listContent()`，
  CLI **没有删除能力**，微头条泄漏只能人工去后台删。
- **ADR-0059 / ADR-0062**：误发的那篇重复文章，「平台允许删除，但 CLI 没有 delete 命令，
  只能人工在头条 Web 后台删」，账本里挂着 `needs_human_delete` 天天提醒。

三条结论合起来是：**能力缺失被记了三次，三次都推给了人。**

## 发现

### 一、两个端点都在平台自己的代码里，不用猜

发布子应用是微前端（`pgc_web_v4_publish/1.0.1.1979`）。它的 `index.ab4194ac9d.js`
里有现成的封装：

```js
l = function(e){ return U2("/mp/agw/article/edit", {pgc_id: e, wxstyle: 0, format: "json"}) }
```

```js
e.prototype.Delete = function(e, t){
  var r = Xl({type:e.type, gid:e.gid, slave_id:e.slave_id, ...});
  var a = "".concat(this.uriPrefix, "/mp/agw/creator_center/delete").concat(r);
  return ferryFetch(a, {method: "POST", headers: o.A, body: JSON.stringify(e)}, t);
}
```

内容管理页的 `index_57f4462f375124ce.js` 里有同一份 `Delete`（`type/gid/slave_id/...`
拼 query，同一个对象做 body），以及编辑态的入口判断：

```js
t.pgc_id && "edit" === t.from && n(!0)   // /graphic/publish?pgc_id=...&from=edit
```

### 二、`/mp/agw/article/edit` 的响应**没有 `data` 外壳**

列表、登录这些接口都是 `{"code":0,"data":{...}}`。这个端点把文章对象平铺在顶层
（`title` / `content` / `media` / `pgc_feed_covers`），实测 2026-10-30。

照抄别的端点的解析方式会静默拿到空 dict —— 然后 `edit` 以为原标题是空串，被自己的
标题闸拒掉。**看起来像闸太严，其实是解析错了。**

### 三、改稿有次数上限

详情里有 `remain_modify_count`（当天实测 5）与 `show_remaining_times`。
每次改写消耗一次。**这是「改稿」和「发布」最大的行为差异**：发出去是一锤子，
改是有限次的。

### 四、`7050「保存失败」不是签名闸（推翻了旧结论的一半）

旧文档把写路径失败归给签名。实测推翻了它：

| 请求 | 返回 | 说明 |
|---|---|---|
| 空 body | `7050 保存失败` | 旧证据，被解读成「穿过了签名闸」 |
| `save=99`（非法值） | **`4029 标题长度应该在 2-30 字之间`** | **`save` 被解析了** → 请求进了字段校验 |
| 合法 `save` + 真实编辑器 HTML + 真实封面 | `7050` | 仍然失败 |

`/mp/agw/article/publish` 确实在 `bdms` 的 `paths.include` 里（连同
`/mp/agw/article/wtt`、`/mp/agw/draft/save_ugc_draft`），但**这条闸没有拦下**不带
签名的纯 HTTP 请求 —— `save=99` 能被字段校验接住就是反证。

所以 7050 是**表单字段还不够**，不是签名。缺的东西比标题靠后。要推进只能抓一次
真实发布请求的完整 body。**这是下一件事，不是现在能猜出来的。**

### 五、`delete` 不受此影响

`/mp/agw/creator_center/delete` **不在**签名清单里。用不存在的 gid 打过去，返回的是
业务错误而不是风控拒绝：

| type | 返回 | 含义 |
|---|---|---|
| 0 | `1002 无效题材类型` | 0 不是合法题材 |
| 1–7 | `1009 无效 ID` | **题材合法**，只是 id 不存在 |
| 8, 9 | `1002 无效题材类型` | 越界 |

`1009` 是这一轮最重要的一个数字：它证明请求被正常解析、参数被正常校验。

## 决定

### 一、`detail` 进只读区，随便用

`article_detail()` 是 `GET`，无副作用，不需要任何开关。它是删除与改写的前置：
**改之前必须知道现在是什么**。

### 二、删除与改写都是「两条闸 + 一次反查」

```
标题闸：平台当前标题 == --expect-title，否则拒绝
风险闸：--allow-unverified-write，否则拒绝
反查：写完/删完再读一次平台，不信返回值
```

**标题闸是核心。** gid 是 19 位数字，抄错一位就是另一篇文章。一旦传错，后面所有
校验都是对着错的对象做的。先读回平台上的标题再比，是这两条命令唯一防得住手滑的地方。

### 三、改稿前先落快照

`.newsagg/snapshots/<gid>-<时间戳>.json`，含改前的 `title` / `content` / `cover`。
改坏了能对回去 —— 这不是「以防万一」，改写不可逆且消耗次数，没有快照等于没有退路。

### 四、不重新上传封面

不改封面就沿用 `pgc_feed_covers[0].origin_uri`，不发上传请求。上传会在账号图库里
永久多一张图且删不掉（ADR-0032 对封面的同一条理由）。

### 五、编排器不调用这两条命令

这是 **ADR-0017 的边界**，不是疏忽：`run_all.sh` 不调用 `edit` / `delete`。
它们是**人手里的刀**，不是自动化流水线上的工序。补全能力 ≠ 放开自动化；
这条线由「谁在调用」决定，不由「CLI 有没有这个命令」决定。

## 验证记录（2026-10-30）

| 操作 | 结果 |
|---|---|
| `detail --gid 7702446362884948530` | ✅ 标题 + 2472 字正文 + 封面 + 剩余可改 5 次 |
| `delete`（不给 `--allow-unverified-write`） | ✅ 拒绝，退出码 1 |
| `delete --expect-title "编造的标题"` | ✅ 标题闸拒绝，并打印平台上的真实标题 |
| `delete` 打不存在的 gid（type=0/1/8） | ✅ `1002` / `1009` / `1002`，请求被正常解析 |
| `save_draft` 真实 HTML + 真实封面 | ❌ `7050`，表单字段未对齐 |
| `edit`（借 publish 端点） | ❌ 同上，已在错误信息里写明原因与下一步 |

**没有删除任何真实作品。** 删除路径的正确性只做到「参数被服务端接受」这一层，
因为唯一能验证到底的办法是删掉一篇真东西，而现有没有可弃目标。

## 未解决

1. **`type` 与题材的映射没确认。** 1–7 都合法，但哪个是图文、哪个是视频、哪个是
   微头条，没有证据。CLI 默认 `--type 1`，第一次真删之前应当在**可弃目标**上确认，
   并把结果记进本 ADR。
2. **publish 表单缺字段。** 这是修改能力真正的拦路石。可行的下一步是浏览器端拦截
   一次真实发布请求，把 body 逐字段对下来 —— 在此之前，`edit` 走浏览器后端或
   平台后台。
3. **`remain_modify_count` 的消耗语义未验证。** 只知道它存在且会减少。

## 补记（2026-10-30 深夜）：抓包做了，结论反转

上一节第 2 条当晚就执行了。用 Playwright 在 route 层 `abort` 拦下真实请求（零写入），
拿到了完整的 `article_publish` body：**27 个字段**，`content-type` 是 urlencoded，
URL 上带 `msToken` 与 `a_bogus`。

### 一、「不是签名问题」这个判断被推翻了一半

把抓到的 body **原样重放**（含 `msToken` / `a_bogus`），仍然 `7050`。

所以正确的表述是：

- 字段校验**确实**在签名之前跑（`save=99` → `4029` 是真证据）；
- 但保存这一步另有环境绑定，**签名参数抄过来也没用** —— 它绑的不只是参数串，
  还有请求环境（TLS/UA/头序/时间）。urllib 复现不了。
- 结论：**纯 HTTP 写路径不可用**，ADR-0073 的判断成立。本文档「不是签名问题」那句
  收窄为「不只是签名问题」。

### 二、编辑只能走浏览器，而且有三处坑

真机跑下来，浏览器改一篇已发布文章需要：

| 环节 | 做法 | 坑 |
|---|---|---|
| 标题 | `inputValue()` 校验后 `fill()` | 无 |
| 正文 | **真实剪贴板**（`navigator.clipboard.write` + `Ctrl+V`） | 合成的 `ClipboardEvent` ProseMirror **不认**，DOM 变了但状态机没变，发布出去的还是旧正文 |
| 发布 | 点 `button`（不是里面的 `span`） | 点 span 只弹出预览 |
| 校验 | 读「共 N 字」 | 这是唯一能证明状态已提交的信号（本次 3602 → 2159） |

### 三、平台在「修改审核中」期间锁死编辑

标题改完后，文章进入 `修改审核中`；此时再打开编辑页，单选框列表为空、点发布不发请求
（不是按钮禁用，是表单根本不渲染）。任何自动化在这个窗口内都会「点了没反应」，
必须等审核结束。

### 四、修改会消耗次数，且可能只生效一部分

本次两次提交：第一次只改了标题（正文因为合成 paste 没进状态机），第二次提交正文。
`remain_modify_count` 5 → 4 → 3。**平台允许「部分生效」**：标题先上线，正文等审核。
这意味着一篇正在审核中的文章，读者看到的可能是「新标题 + 旧正文」。

### 五、今晚的实际结果

- 线上标题已改为《谷歌一天少5000亿：市场不再给「没有顶」的资本开支付钱》
- 正文修改已提交，`修改审核中`；审核通过前线上正文仍是旧版
- 改前原文完整快照：`.newsagg/snapshots/7702446362884948530-20261030T234906.json`

**因此 `edit` 子命令的 HTTP 实现保留但标记为不可用**：它会在 7050 处给出解释性错误，
而不是假装成功。要真正改稿，用浏览器后端或后台手动编辑。

## 补记二（2026-10-31 凌晨）：浏览器自动化也走不完，改稿交回人

审核通过后再试了三轮。**正面结论是「能改标题」，负面结论是「改不了正文」**，
而且过程中把文章改成了新旧两版拼接的坏状态。以下是实测到的四条，任何一条都足以
否掉「自动化改正文」这条路：

### 一、封面没选 → 点发布静默失效

改过一次之后，编辑页加载出来时**封面选择被清空**（`单图` 未选、但图还在）。
此时 `发布` 按钮 `disabled=false`、点击不报错、**不发任何请求**、也不滚到校验区。
把「单图」选回来，请求立刻发出。这是当晚最贵的一个坑：没有任何反馈信号。

### 二、`Ctrl+A` 不保证选中整篇 → 粘贴变成插入

标题栏点过一次之后进正文执行 `Ctrl+A`，ProseMirror 只选了当前块，粘贴于是**插在
光标处**：旧版 6 个 H1 + 新版 2 个 H1，正文 6467 字，两版并存。
可靠做法是**编辑器内** `document.execCommand('selectAll')` + `Delete`，
并验证「共 N 字」归零。

### 三、正文替换之后，发布请求再也不发

清空 + 真实剪贴板粘贴（字数 3602 → 2159 已验证进状态机）之后，
无论鼠标坐标点击还是 JS `b.click()`，`/mp/agw/article/publish` **一次都不发**；
而同一次会话里只选封面、不动正文时点发布是能发出去的。日志显示粘贴后编辑器在跑
`word_check` / `spell_check_apply`，提交被卡在签名 SDK 那一层（`_signature` 由
拦截器在发出前追加）。**结论：这条路在自动化下不可用，不是选择器问题。**

### 四、刷新会丢掉粘贴

想用「自存草稿 + 刷新让 SDK 重新初始化」绕过，实测刷新后正文回到已发布版本
（0 字 → 又变 63 块旧内容），自动保存不覆盖 ProseMirror 的粘贴结果。

### 五、平台允许「部分生效」，代价由文章承担

标题先上线、正文等审核，中间态是**新标题 + 旧正文**；再叠加第二条，就成了
新旧两版拼接。这类中间态对外可见，而 `remain_modify_count` 只剩 1 次。

**最终决定：正文修改不再自动化。** 人点浏览器是唯一稳的路径——真实的点击会带着
SDK 现场的 `_signature`，这正是我们复现不了的那一层。CLI 保留 `detail`（读）
与 `delete`（删），`edit` 仅作为「会明确失败并解释原因」的入口存在。



## 后果

- **好的**：ADR-0047 / 0059 / 0062 里那三句「CLI 没有删除能力，只能人工去后台」
  不再成立。误发的重复文章、测试草稿，现在有一条带闸的命令可以处理。
- **好的**：`detail` 让「线上到底是什么样」第一次可以在脚本里读到（此前只能靠
  `list` 的摘要猜）。
- **代价**：多了一个不可逆命令。防线是标题闸 + 风险闸 + 反查，而不是「没人会手滑」。
- **仍然诚实的部分**：`edit` 现在是**不通的**，且它会在错误信息里说明白为什么不通。
  一个 7050 加一句「字段没对齐，别猜」，比一个看起来成功、实际改了半篇的结果好。
