# ADR-0038：无人值守接线——编排器补齐九步、三段式交接、看守改读仓库

## Context

ADR-0002 定「用 Skills + DSH 定时任务实现流水线，不自建常驻服务」，ADR-0026 定了九步时序，
ADR-0018 定了「云端每次运行前 `git pull --rebase`、运行后 `commit + push`」。

在真正要把它接到定时任务上时，实测发现三处落差，任何一处都会让「无人值守」变成
「每天自动跑一遍、然后什么都不沉淀」：

1. **`run_all.sh` 只实现了九步中的五步。** 它的头部注释声称实现 ADR-0026 的时序，
   但全文件 `grep -n "git \|writeback\|pull\|commit\|push"` **零命中**——既没有
   `git pull --rebase`，也没有认知写回（`writeback.py`），也没有 commit/push。
   后果：风格回路每天学的都是旧基线（本人改的稿永远进不了系统，因为没人 pull）；
   观点卡不再累积 `covered_events` 与修订史（认知资产停止生长）；产出留在本地不入 git。
2. **简报从未开过 GitHub Issue，而看守按「issue 是否存在」判主系统存活。**
   全仓 `gh issue create` 零命中，`brief.py` 只写 `reports/<日期>.md`。于是看守每天
   都会发一封「主系统可能整体失效」的**假警报**，把全系统唯一的推送通道（ADR-0006
   第四条 GitHub Actions 原生邮件）占满——这比没有告警更糟，因为它训练人忽略告警。
3. **编排器把执行切成两段就 `exit 0`。** 分拣的**判断**必须由模型做（ADR-0025），
   而脚本不能自己调用模型。原实现只打印一段指引就退出，定时任务无法无人值守地续跑。

另外两处需要在接线时一并处理：`.newsagg/` 的 5 个文件在 `.gitignore` 生效前已被追踪，
与 ADR-0027「双环境各自持有、不入库以免冲突」直接矛盾；Q81 要求的 `.env.example` 不存在。

## 发现

### 一、分拣判断必须由模型完成，这决定了编排器只能是「三段式」

`newsagg-triage/SKILL.md` 的七条硬规则（冷却期优先、新进展判据、可复用性门槛、
低置信度不参与竞争、允许弃权……）没有一条能被确定性脚本执行。因此编排器在
「组装分拣输入包」之后必须**把控制权交回 agent**，等 agent 写完 `decision.json`
并用 `triage.py --validate` 校验通过后，再被 `--after-triage` 重新唤起。

同理由 `--after-write` 承接：`wewrite llm-write` 在未配置写作模型时返回**退出码 3**，
这是 wewrite 设计上的降级信号（源码注释：`0 成功；3 未配置写作模型（→ 降级为 agent 自写）`），
此时初稿也要由 agent 写。于是「一次运行」被切成三段：

```
--no-collect        → ① pull ② 风格学习 ②b 表现数据 ②c 跳过日门 ③ 采集 ③b 组包
                      然后交回 agent（写 decision.json + 校验）
--after-triage      → ④ 组 brief（弃权则直接出简报收尾）；跑 llm-write；交回 agent 写成稿
--after-write       → ④b 封面 ⑤ 发布 ⑥ 写回 ⑦⑧ commit+push ⑨ 简报
```

三段必须共享 `--date`，否则跨段会读到不同日期的文件（跨零点运行时）。

### 二、白天三次采集若覆盖写，恰好丢掉多次采集想捕捉的东西

ADR-0006 定「采集每日 2–3 次」的理由是**捕捉事件发酵过程**。但 `collect.py` 是
`out_path.write_text(...)` 覆盖写，同日第二次采集会把第一次的候选整份替换掉——
热度爬升的中间值、以及"某条先出现、后来掉出榜"这类信号全部丢失，等于白采。

改为按 `(source, id)` 归并累积：保留 `first_seen`，热度轨迹写进 `hot_history`，
本轮没再出现的条目保留并标 `seen_in_last_run: false`（**不静默丢弃**——"掉出榜"
本身就是信息），每次采集追加一条 `collection_runs`。

这里踩到一个真实缺陷并已修复：最初只在"旧文件存在"时才走合并，于是**当日第一次
采集**产出的条目没有 `first_seen`/`hot_history`，第二次合并时无轨迹可续，
`runs_today` 也永远停在 1。修正为即使无旧文件也以空池为底走同一路径。

### 三、`.newsagg/` 不入库，所以「本轮运行失败了」这件事没有出口

ADR-0027 定 `.newsagg/` 是运行时状态、本地与服务器各自持有、不入库（否则两环境
互相冲突）。但看守跑在**另一台机器**上（ADR-0006 要求如此，否则与主系统同生共死），
它读不到 `.newsagg/`。于是主系统"今天跑挂了"与"今天没选题"在外部仍然不可区分——
而这正是 ADR-0019 五段式简报要解决的问题。

解法：编排器**无论成败**都把本轮成败写进 `.newsagg/run-status.json`，并由简报把它
呈现到 ① 段与 ⑤ 段（这两段都入库）。失败时 ① 段显式写「**本轮运行未完成**」而不是
「无决策记录」，并注明「这不是今日无选题，也不是弃权」。`run-status` 只在日期匹配
时才被采用，避免昨天的失败写在今天的简报里。

## Decision

1. **`run_all.sh` 补齐 ADR-0026 的九步。** ①`git pull --rebase`（冲突即 `git rebase --abort`
   + 熔断 `git_conflict` + 告警，**不自行合并**）；⑥`writeback.py`（仅在 `--mode publish`
   且决策给出 `card_file` 时，且只在发布成功之后）；⑦⑧`git add -A` + commit + push。
2. **三段式交接**，参数为 `--no-collect` / `--after-triage` / `--after-write`，
   全部接受 `--date`。旧参数 `--after-triage` 语义保留但扩展。
3. **失败必须出简报。** 新增 `fail_soft`：任何阶段失败都先写 `run-status`、再出简报、
   最后尝试 push（合并冲突与 pull 失败除外——那时远端状态不明，不 push，交人工）。
   `fail_soft` 替代原先的直接 `die`。理由是 ADR-0006 的硬性要求：**简报必须无条件每日存在**。
4. **`.env` 由编排器显式加载**（`set -a; source .env; set +a`）。定时任务由调度器直接
   拉起、不经过交互式 shell，不能依赖人工 export。同时新增入库的 `.env.example`（Q81）。
5. **采集改为同日累积合并**（`merge_candidates`），新增 `--no-merge` 逃生开关。
   覆盖写只在显式要求时发生。
6. **看守改读仓库里的 `reports/<日期>.md`**（`actions/checkout` + `cat`），不再查 issue、
   不再依赖 `gh`。这是对 ADR-0020「简报 issue 命名约定」的**有意偏离**：主系统从未实现
   issue 双写，而看守的职责是发现"主系统整体失效"，它不该依赖一个从未被实现的机制。
   issue 双写若要恢复，应作为独立工作另开，不能与看守的正确性绑在一起。
7. **看守仍只判「存在且五段齐备」**，不解析运行成败。一份写明「本轮运行未完成」的简报
   仍算"存在"——它比没有简报信息量更大；细节由人在简报里读。看守的职责是发现
   **沉默**，不是判断内容质量。
8. **`.newsagg/` 全部 `git rm --cached`**，与 ADR-0027 一致。本地文件保留。
9. **降频跳过日也走完整收尾**（写 `run-status`、出简报、push），只是不采集、不写作、不发布。
10. **`--no-git` 逃生开关**：跳过 pull 与 commit/push，供本地端到端测试使用。
    默认不跳过——无人值守的沉淀正是靠这两步。

## Consequences

- **编排器现在有 466 行、13 个函数**（本 ADR 落盘时为 435 行 / 11 个函数；其后
  ADR-0039 又补了封面解释器 `COVER_PY` 与 `card_file` 传递，函数数随之增加），
  其中 `git_pull` / `style_learn` / `performance` /
  `collect_now` / `triage_input` / `fail_soft` / `sync_push` / `write_status` 各司其职。
  复杂度换来的是「定时任务只需触发这一个入口」——这正是 ADR-0002 想要的形状。
- **三段式交接把"一次运行"变成三次进程启动**，因此每段都会重新执行 `git pull`。
  第一段与第二段之间的 pull 通常无新提交，成本可忽略；但它也让"跨段期间你 push 了新改动"
  能被正确取得。
- **`fail_soft` 会 push 一个失败状态**。这是有意的：失败也是要沉淀的事实（它进简报、
  进 git 历史），但**失败运行不留教学副本、不触发写回**——写回必须只在真实发布成功后。
- **看守不再依赖 `gh`**，因此主系统所在机器不必安装它（ADR-0005 记录的运维前置就此解除）。
  代价是看守需要 `actions/checkout`，即需要 `contents: read`；它本来就是私有仓，
  这点权限不构成新的暴露面。
- **`collection_runs` 让简报 ② 段能显示"今天采了几次、每次新进来多少条"**。
  这是 ADR-0006「捕捉发酵过程」唯一的可观测形式；没有它，多次采集的效果无法被人验证。
- **`hot_history` 目前只是被记录，还没有消费者。** 分拣目前仍按"当前热度"排序。
  让分拣用上热度**轨迹**（例如"正在爬升"比"已经很高"更值得写）是下一步的优化，
  不属于本次接线；现在只保证这些中间值不再被覆盖写丢掉。
- **仍未解决**：`.env.example` 里的 `CLASH_SUBSCRIPTION_URL` 只在服务器需要，
  本地留空即可；服务器部署（DESIGN.md 阶段 1 第 9 步）尚未执行，因此本 ADR 描述的
  接线目前只在本地生效。ADR-0027 第四条「验证期只跑本地、上线后只跑服务器」意味着
  上线时必须**显式停掉本地定时任务**——两边同跑会同日发两篇。
- **本地定时任务与 DSH 会话绑定。** 到期提醒以普通后续消息投递到原会话
  （`docs/user/guide/schedule.md`），因此它只在 DSH 宿主运行、且该会话能被唤起时才真的触发。
  这比 ADR-0027 第六条警告的「本地定时容易忘记关」更强：它还会**静默地不触发**。
  因此上线后必须核实服务器侧的调度独立于这个会话。
