# 技术分享笔记写作

> **指导思想：费曼技巧**——复杂性与术语黑话往往掩盖理解的缺失，能讲简单才算真懂。写技术笔记不是记录做过的事，而是拿它检验自己有没有真懂：**讲不清楚的地方，就是没搞懂的地方**。
> 好文章通常不是"标题最炸"的，而是在真实痛点上，用可信的方式，带读者走完从问题到解决的完整路径。
> 一句话公式：**高吸引力 × 高收获 = 真实痛点 × 具体结果 × 可复现路径 × 独家信息增量 × 清晰表达**

**吸引查看**靠选题和钩子；**让人有收获**靠信息增量、可操作性和认知升级。两条腿缺一条，要么没人点，要么没人存——费曼技巧管的就是"收获"这条腿。

---

## 写作流程：费曼四步

四步走完再发。哪一步答不上来，就停在那一步补齐，不要硬往下写。

| 费曼步骤 | 这一步要做的 | 对应章节 |
| :-- | :-- | :-- |
| **1 选定概念，画出知识地图** | 只锁定一个概念、一类文章，先把已知的全部列出来 | 一 必答五问 · 二 素材梳理 · 三 选题 · 六 文章类型 |
| **2 讲给 12 岁孩子** | 用不懂这项技术的人也能跟上的措辞写出主线 | 语气基线 · 四 标题公式 · 七 正文结构 |
| **3 复习与精修** | 逐段找讲不透的地方，回原始材料补事实，再重写该段 | 五 四层收获 · 八 信息增量检查 |
| **4 测试与归档** | 按清单全面过一遍；表现好的稿子连同数据留作模板 | 十 发布前自检清单 |

第九节（小红书平台适配）是贯穿全程的硬约束，不属于任何一步，动笔前先读一遍。

## 语气基线（默认必须满足）

- **娓娓道来**：像跟同行复盘一样，把来龙去脉一层层讲清楚。节奏稳，不喊口号、不堆感叹号、不用"震惊""绝了"。
- **不出现第一人称**：标题和正文都禁用"我""我们""咱们"，也避免"你们""大家"这类直接称谓；改用"这次排查""关键改动""实测下来""回头看"等中性说法承载叙事。
- **12 岁测试**：全篇及格线是"不懂这项技术的人也能跟上主线"。逐句读过去，需要回读才能懂的句子就重写；术语、参数、命令照抄不改（见下一条），但第一次出现时要让人看懂它在这里干什么。
- **术语不因口语化打折**：版本号、参数名、命令、报错原文一律原样保留。
- **标题保留具体信息与钩子**，但同样不自称"我/我们"。

> 本节规则优先于下文所有示例；示例已按"无第一人称 + 娓娓道来"书写，不要改回"我/我们"版本。

## 一、动笔前必答五问

1. **读者是谁？**——具体到人，如"写了两年 React、正在做首屏优化的前端" > "程序员"
2. **他现在的痛点是什么？**——越具体、越常见越好
3. **看完他能立刻做什么？**——能跑通的命令/能改的配置/能做的判断
4. **有没有别人没有的数据、实验或经验？**——这就是信息增量，没有就别写
5. **标题有没有诚实兑现内容？**——写完之后回来核对

任何一问答不上来，先回到第二节做素材梳理，不要硬写。

---

## 二、素材梳理：把开发经历变成可写的笔记

有料的技术笔记来自真实经历，不是概念复述。动笔前，把这四件事写下来（缺哪件就回代码/日志里补）：

| 要提取   | 具体问法                                         | 用途       |
| :------- | :----------------------------------------------- | :--------- |
| **现象** | 当时的具体报错/卡顿/异常是什么？有日志或截图吗？ | 开头钩子   |
| **弯路** | 试过哪些没用的方案？为什么不行？                 | 踩坑与边界 |
| **解药** | 最后怎么解决的？关键的那 1-3 处改动是什么？      | 方案与步骤 |
| **对比** | 改前改后的数字是多少？（耗时/内存/包体积/QPS）   | 结果与数据 |

> 一个技术点如果凑不出"现象 + 弯路 + 解药 + 对比"，说明经历还没沉淀够，先别发。

## 三、选题：先让读者觉得这事与自己有关

|  #  | 策略                         | 要点                                                      | 示例选题                                            |
| :-: | :--------------------------- | :-------------------------------------------------------- | :-------------------------------------------------- |
|  1  | **真实且普遍的问题**         | 问题越具体、越常见，点击和收藏越高                        | 线上 OOM 怎么排查、MySQL 慢查询怎么优化             |
|  2  | **有具体结果和数字**         | 数字和结果比"浅谈""初探"更有吸引力                        | 接口响应 2s → 200ms、3 行代码省 40% 显存            |
|  3  | **反常识 / 踩坑 / 失败复盘** | 冲突和教训天然想点开，但必须真实有细节                    | 为什么把微服务又拆回了单体、不要再用这个 Redis 命令 |
|  4  | **蹭对热点 + 独家内容**      | 大模型/RAG/Agent/Rust/WASM 有流量，但纯搬运没收获也不传播 | 拿 1000 条真实问题，测了 RAG 和长上下文             |
|  5  | **标题诚实，承诺明确**       | 好标题有度；标题党骗一次点击，毁长期信任                  | 一次线上事故的完整复盘                              |

**选题自检**：这个痛点常见吗？有没有别人没有的东西？能否在标题里说清读完能拿到什么？这篇是否只讲一个概念（多个概念就拆成系列，一篇塞两个概念读者会失焦）？

## 四、标题公式

> 好标题 = **具体场景 + 明确收益 + 适度情绪**；差标题 = 夸张、模糊、标题党。

### 8 种技术标题公式

|  #  | 公式          | 结构                         | 示例                                   |
| :-: | :------------ | :--------------------------- | :------------------------------------- |
|  1  | **数字+结果** | `[动作]，[结果数字]`         | "改了 3 处，接口从 2s 到 200ms"        |
|  2  | **反常识**    | `[常识]，其实[真相]`         | "微服务不是银弹，最后还是拆回了单体"   |
|  3  | **避坑警告**  | `别再[错误]，[后果]`         | "别再这么用 Redis 了，线上直接阻塞"    |
|  4  | **事故复盘**  | `一次[事故]的[数字]个教训`   | "一次删库事故的 7 个教训"              |
|  5  | **方案对比**  | `[A] vs [B]，[条件]下选哪个` | "RAG vs 长上下文，1000 条真实问题测完" |
|  6  | **身份锁定**  | `写[技术]的都踩过[坑]`       | "写 Go 的都踩过这个 slice 的坑"        |
|  7  | **结果前置**  | `[结果]，只做了[简单动作]`   | "显存省了 40%，只改了 3 行代码"        |
|  8  | **知识地图**  | `[主题]知识地图，一页搞懂`   | "Redis 知识地图：一页纸理清"           |

### 技术标题硬约束

1. **≤20 字**（emoji 算 1 字，UTF-16 计数见流水线脚本），超了信息流被截断
2. **前 10 字含核心搜索词**（如"Redis""首屏优化""OOM"），搜索权重集中在标题前段
3. **承诺必须兑现**：标题里的数字、结论、场景，正文里都要有对应内容
4. **emoji 可选**：技术笔记信息优先，可放 1 个做视觉锚点，不放也不算错；放就放开头且每篇不重复，不堆叠

### 标题废词黑名单

> 这些词零搜索量或零信息增量，只占字数。写完逐词扫描删除。

`浅谈` `初探` `漫谈` `随想` `那些事` `一篇就够了` `深度好文` `万字长文` `干货` `宝藏` `炸裂` `封神` `YYDS` `必看` `揭秘`

**反例**：`浅谈前端性能优化` → **正例**：`首屏从 4s 到 1.2s，只做了 3 件事`

## 五、四层收获（读者看完能带走什么）

> 收藏率的根因是"有用"。有用 = 读者能带走东西。

|    层次    | 目标           | 怎么做到                   | 对应内容 |
| :--------: | :------------- | :------------------------- | :------- |
|  **能跑**  | 可直接复制     | 代码、命令、配置、环境版本 | 方案步骤 |
|  **能懂**  | 知道为什么     | 解释机制，而不只给做法     | 原理支撑 |
|  **能选**  | 能自己做决策   | 对比成本、边界、适用场景   | 方案对比 |
| **能迁移** | 能用到自己项目 | 提炼方法论                 | 总结清单 |

**自检**：这篇至少命中 2 层，主力内容争取 4 层。只给结论不给过程 = 只到"能懂"；只贴代码不解释 = 只到"能跑"。

---

## 六、7 类高价值文章类型

| 类型         | 核心要素                   | 必备证据                       |
| :----------- | :------------------------- | :----------------------------- |
| **实战教程** | 从零到一，手把手           | 可运行代码、环境版本、完整步骤 |
| **深度原理** | 源码/协议/架构解析         | 关键源码行、调用链、图示       |
| **性能优化** | 有前后对比数据             | 优化路径 + 压测/监控对比       |
| **故障复盘** | 时间线、根因、修复、预防   | 时间线、日志、根因、改进项     |
| **方案对比** | A vs B，给决策依据         | 对比表格 + 各自边界条件        |
| **前沿实验** | 新模型/框架/工具第一手测试 | 测试方法、数据、局限           |
| **系统总结** | 零散知识整理成体系         | 结构图 + 可复用的知识地图      |

选一类为主。不要在一篇里既当教程又当复盘，读者会失焦。

## 七、正文结构（8 段）

```
1. 开头 3 句    → 说清痛点、场景、读完能获得什么
2. 背景与问题    → 为什么这事重要，别人怎么做的
3. 方案与步骤    → 代码 / 命令 / 配置，逐步可复现
4. 结果与数据    → 截图 / 压测 / 对比表格
5. 踩坑与边界    → 失败尝试、限制条件、适用场景
6. 原理与解释    → 为什么有效，底层机制
7. 总结与清单    → 读者能直接带走的要点
8. 延伸资源      → 仓库、文档、系列文章
```

### 开头 3 句：决定生死

小红书正文预览只显示前 40-50 字。这几十字不是"背景介绍"，是"最后一道门"。

| ❌ 废开头                                    | ✅ 钩子开头                                                      | 为什么有效         |
| :------------------------------------------- | :--------------------------------------------------------------- | :----------------- |
| "随着微服务架构的普及，越来越多的团队开始……" | "服务数到 30 个之后，一次改动要发 5 个 repo。最后决定拆回单体。" | 具体场景+冲突      |
| "今天给大家分享一下 Redis 的使用经验。"      | "上周线上卡了 40 分钟，最后定位到一条本可以避免的命令。"         | 数字+悬念          |
| "本文介绍 React 性能优化的几种方法。"        | "首屏 4.2s，用户流失一半。改完 1.2s，只动了 3 处。"              | 结果前置           |
| "在当今大模型快速发展的背景下……"             | "RAG 和长上下文到底选哪个？拿 1000 条真实问题跑了一遍。"         | 直接给读者要的答案 |

**开头四原则**：不铺垫背景 / 不结论先行 / 给具体的人+具体的麻烦+具体的数字 / 制造微小悬念或认知落差。

### 各段落地要点

- **方案步骤**：明确环境与版本（OS、语言、框架、依赖版本）；命令可直接粘贴；关键行加注释
- **结果数据**：用表格或截图，给"改前 → 改后"，说明测试条件（数据量、机型、并发）
- **踩坑边界**：写清楚什么场景适用、什么场景别用；没走通的路也是稀缺信息
- **原理**：从源码/协议/架构层面解释现象，这是"能懂"和"能迁移"的来源

## 八、信息增量检查

> 有收获 = 要么新数据，要么新实验，要么新视角。三者一个都没有，就是搬运。

|   等级    | 增量类型                 | 示例                                                        | 收藏驱动力 |
| :-------: | :----------------------- | :---------------------------------------------------------- | :--------: |
|  🥇 一级  | **独家数据 / 实验结论**  | "1000 条真实问题下，RAG 命中率 71%，长上下文 88% 但贵 6 倍" | ⭐⭐⭐⭐⭐ |
|  🥈 二级  | **可复现路径**           | "环境 + 命令 + 关键配置，照着跑就能复现"                    |  ⭐⭐⭐⭐  |
|  🥉 三级  | **具体版本 / 边界条件**  | "该问题在 v3.2 修复，v3.1 及以下必踩"                       |   ⭐⭐⭐   |
| ⚠️ 伪增量 | 官方文档转述、形容词堆砌 | "Redis 性能非常优秀，值得深入学习"                          |     ⭐     |

**检查方法**：逐段问"这段有别人查不到的东西吗？"没有就删或合并。全篇至少 1 个一级或 2 个二级增量，否则重新选题。

**精修动作（费曼第 3 步）**：讲不透的段落不是润色问题，回原始材料把事实补齐——代码、日志、官方文档、压测记录——再重写这一段。用形容词糊过去，等于承认这段还没搞懂。

## 九、小红书平台适配

- **正文 ≤1000 字**（平台硬限制）。技术长文优先拆成图文卡片（配图用 xhs-card-skill）或系列笔记，正文放主线 + 结论。
- **代码与命令**：正文只留最短的可运行片段（3-10 行）；完整代码、配置、日志放配套图卡或截图，别把正文塞满代码。
- **首图**：承担"标题 + 核心结果数字"双重职责，和笔记标题形成组合拳。
- **口语化**：说"你"不说"用户"，说"踩坑"不说"经验教训"；但技术术语要准确，别为了口语牺牲严谨。
- **标签**：放最后一行，形如 `#前端性能优化 #Redis`，2-5 个，含主搜索词。
- **合规红线**：不晒收入数字、不放二维码/微信号、不用"扣1/免费送/帮你"等利益交换话术；外部仓库链接以文字提及为主，不做导流话术。

## 十、发布前自检清单

**选题与标题**

- [ ] 五问都答得上来，信息增量至少 1 个一级或 2 个二级
- [ ] 标题 ≤20 字，前 10 字含核心搜索词，无废词黑名单词
- [ ] 标题里的数字/结论，正文都能兑现

**内容**

- [ ] 前 40 字是钩子，不是背景铺垫
- [ ] 按 8 段结构走完"问题 → 解决"完整路径
- [ ] 有环境与版本、有可复现步骤、有改前改后数据
- [ ] 写了踩坑与边界（适用/不适用场景）
- [ ] 解释了原理，而不只给做法（至少到"能懂"）
- [ ] 至少有 2 层收获（能跑/能懂/能选/能迁移）
- [ ] **语气达标**：娓娓道来，全文无"我/我们/你们/大家"，无喊口号式表达
- [ ] **12 岁测试过关**：逐句读过，没有需要回读才能懂的句子；术语照抄，但都说明了在这里干什么
- [ ] 全篇只讲一个概念
- [ ] 讲不透的段落都已回原始材料补齐并重写，没有靠形容词糊过去

**平台**

- [ ] 正文 ≤1000 字，代码片段精炼，长代码已转为图卡
- [ ] 标签含主搜索词，放最后一行
- [ ] 无合规红线词，无外部导流话术

**收尾**：结尾给可带走的总结清单或一句方法论，不用"评论区聊聊"式空 CTA；需要互动就用一个真问题，如"你线上遇到过同类问题吗？"
