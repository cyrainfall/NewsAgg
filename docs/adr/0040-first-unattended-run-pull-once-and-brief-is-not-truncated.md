# ADR-0040：首次真实无人值守运行的两处缺陷——续跑段不得再 pull、简报理由不得硬截断

## Context

ADR-0038 把 `run_all.sh` 补成九步编排、切成三段交接；ADR-0039 记录了端到端实测中
发现的三处接缝缺陷并修复。但那一轮端到端验证大量使用 `--no-git`（绕过 git 同步），
所以 git 路径没有被真实压到。

2026-10-17 21:00，4 条 DSH 定时任务中的主流程第一次由调度器真实拉起（此前 18:00
的采集任务已先触发一次）。第 1 段（`--no-collect --publish`）与分拣判断都正常，
但第 2 段（`--after-triage --publish`）在开头的 ① `git pull --rebase` 处失败：

```
错误：不能变基式拉取：您有未暂存的变更。
错误：请提交或贮藏修改。
```

`fail_soft` 按设计仍然产出了五段齐备的简报（`run_ok: false`），但这一天的写作、
发布、写回全部没有发生——**而且第 1 段已经写好的东西（表现数据、候选池、输入包）
也永远不会落地**。

## 发现

### 一、`git_pull` 在三段分支之外，被调用了三次——这是一个必然触发的缺陷

`git_pull` 原本位于三段分支**之外**（旧 `run_all.sh:324`），因此第 1、2、3 段
各调用一次。但：

- `reports/performance.jsonl` 是**入库文件**（ADR-0018/0037：跨环境保留阅读率基准，
  必须入 git）；
- 第 1 段的 ②b 表现数据读回**每轮都会改写它**（实测 `1 file changed, 1 insertion(+),
  1 deletion(-)`）。

所以**第 1 段跑完，工作区必然是脏的**；第 2 段一进来就 `pull --rebase`，必然撞上
自己刚写的文件。这不是合并冲突（远端没有新提交），是**预期状态**；但 `git_pull`
当时只区分了"合并冲突 → 熔断"与"其他失败 → fail_soft"，两种处理都会终止这一天。

后果比单次失败更严重：**每一轮无人值守运行都会死在第 2 段**，且第 1 段的产出永不
落地。系统看起来在按时跑、也出了简报，实际什么都不沉淀。

为什么 ADR-0039 的端到端没踩到：那一轮用 `--no-git` 跑通主流程，`git_pull` 直接
`return 0`，恰好绕过了唯一会失败的路径。这是"测试覆盖了代码路径、没覆盖真实配置"
的典型案例——`--no-git` 是开发便利，不是生产形态，用它验证生产路径本身就不成立。

### 二、简报把需要人否决的理由硬截断在半句

同一天的简报还暴露了 `brief.py` 的一组硬截断（`[:60]` / `[:160]` / `[:300]` 等）：

- 「值得关注但无卡可接」的 `why` 被切在
  「…已在与 Meta 开源簇的排序中**让**」——句子没了，而完整结尾是
  「…让位；**建议列为下一轮新建卡的首选**」。被砍掉的恰好是唯一的行动建议。
- 「排序说明」被切在备选二的中间。
- 早期手工验证轮次的 `collection_runs[].kept_new` 是 `None`（ADR-0039 之前的格式），
  `r.get('kept_new', '?')` 的默认值不生效（键存在、值为 None），简报印出
  「13:21（新 ?）」这种读者无法理解的占位符。

ADR-0019 明确简报是本系统真正的**人机接口**，⑤ 段承载所有需要人否决的机制。
把理由按字符硬切，等于让这个人机接口在信息最关键的地方变哑巴——而且因为截断是
静默的，读简报的人不知道自己漏看了后半句。

## Decision

1. **① pull 只在整轮运行的开头执行一次。** `git_pull` 移进第 1 段分支内；续跑段
   （`--after-triage` / `--after-write`）不再 pull。整轮运行中途工作区必然是脏的，
   这是设计使然（入库的 `performance.jsonl` 每轮被改写），不是异常，因此也不应再
   触发任何同步动作。同步只发生在两个时刻：整轮开头取本人编辑、整轮结尾 push 产出。
2. **脏工作区上的"不能变基"不进入熔断分支。** 真正需要熔断的仍是 ADR-0018 的
   合并冲突（本人与系统改了同一处）；"您有未暂存的变更"在 pull 一次的新结构下
   不应再出现。本 ADR 不放宽冲突判定，只消除误触发它的调用方式。
3. **简报中的长文本一律按句截断，不按字符硬切。** 新增 `clip(text, limit)`：
   超限时优先在中文句末标点（。？！；）或英文 `. ` 处断开（断开点须在 limit 的
   一半之后，避免几乎全砍），单句本身超长才退回硬切并加省略号。同时把各字段的
   限额放宽到能容纳真实长度（实测：理由最长 176 字、排序说明 328 字）：
   事件标题 120/200、跳过与无卡理由 400、排序说明 800、新建卡可复用性 300。
4. **渲染层对历史数据负责。** `kept_new is None` 渲染成「未记录」而不是「?」。
   ADR-0039 修了生产者（新数据一定有该字段），本 ADR 修消费者（旧数据仍会被读到）——
   只修生产者会让历史日期的简报永远带着看不懂的占位符。

## Consequences

- **"pull 一次"隐含一个前提：整轮运行期间不会有需要拉取的远端变更。** 三段交接在
  无人值守下是同一条会话连续完成的（间隔以分钟计），本人在此期间 push 的概率极低；
  若真的 push 了，结尾 `sync_push` 的非快进失败会暴露它，下一轮开头的 pull 再收敛。
  这比"每段都 pull、必然死在脏工作区"可接受得多。
- **`clip` 的限额是经验值不是规格**（与 ADR-0014/0016 同策略）：按当前真实长度留了
  余量，但没有结构性保证。未来若某条理由写得极长，仍可能被按句砍——按句砍至少
  保证每一段可读，且不会静默地把行动建议藏在半句里。
- **本 ADR 与 ADR-0039 是同一主题的延续**：无人值守的失败集中在"段与段的接缝"与
  "机器替代人做衔接的地方"。ADR-0039 是日期/解释器/字段缺失，本 ADR 是重复的 git
  动作与静默的文本截断——共同点是**手工分步执行时人会自然补上，交给调度器后才暴露**。
  教训固化为一条：涉及 git 与对外呈现的路径，端到端验证必须用生产形态（真 git、
  真数据），不能用 `--no-git` 这类开发开关替代。
- **首个由调度器触发、完整跑通并真发的闭环在修复后成立**：2026-10-17

  已覆盖事件与未复核修订，简报五段齐备并随 `1553a16` 推送。
