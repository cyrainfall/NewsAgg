# 提交前读回校验、模型配置项、简报 issue 命名约定

## Context

三条收尾决策，共同点是**让系统的内部状态可被外部校验**，而不是只能自证。

**其一：不可逆动作前缺少校验。** ADR-0013 的三道门校验的是**内容**（合规、信用分、封面），但没有一步校验**表单实际填了什么**。而平台 UI 变更会导致选择器漂移，其表现恰恰是"填错了但不报错"——标题写进正文框、分类没选中、封面未上传成功，脚本却认为一切正常。发布是唯一不可逆的动作，因此这是唯一会**发出垃圾内容**的失败模式，也是三道门都拦不住的一种。

**其二：模型选型写死会过期。** 分层策略（分拣用便宜模型、写作用强模型）已定，但具体型号不宜写进设计文档。

**其三：看守需要一个可程序校验的存在性判据。** ADR-0006 让看守检查"今日简报 issue 是否存在"，但"存在"需要约定才能判定，且只看存在无法发现**简报残缺**。

## Decision

**提交前读回校验。** 在真实发布点击"发布"之前，读回表单当前内容（标题、正文首尾段、分类、封面是否已上传），与预期逐项比对；不符即熔断且**不提交**，并截图存档。这是第四道门，校验的是"表单是否真的填对了"，与前三道门校验"内容是否该发"互为补充。

实现落点：`toutiao-ops` 的发布是「预览并发布」→「确认发布」两步，校验插在第一步之后、第二步之前（ADR-0024）。

**发布后反查验证（第五道，在发布动作之后）。** 因为 `toutiao-ops` 的发布是乐观返回（点完按钮即 `success: true`，未验证真的发出），因此发布后必须用 `content list` 反查该标题是否存在于作品列表。三种结果：

| 反查结果 | 判定 |
|---|---|
| 查到，状态 `published` | 发布成功 |
| 查到，状态 `reviewing`（审核中） | **视为已成功提交**，不是失败 |
| 查到，状态 `rejected` | **告警**——内容违规信号，直接关系信用分风险 |
| 查不到 | 视为未发出，走 ADR-0011 的核实流程，**不重发** |
| 核实不清 | 熔断等人 |

**模型型号做成配置项。** 设计层只固定分层策略，不固定型号；上线前用真实数据实测选定。避免文档里的型号很快过期并变成误导。

**简报 issue 命名约定。** 固定标题格式（如 `NewsAgg 简报 YYYY-MM-DD`）+ 固定 label。看守按**标题 + 日期 + label** 三者判定存在性，并校验五段是否齐备（因而能发现"存在但残缺"）。已处理的简报 issue 由本人**手动关闭**，关闭动作本身即"已读"信号。

## Consequences

- 读回校验使发布链路多一次页面读取与比对，且比对逻辑本身可能出错（比对规则过严会导致正常发布被误拦）。这是为消除"静默发错内容"这一**不可逆**失败而付的代价，方向是宁可误拦不可误发。
- 读回校验无法覆盖"平台在服务端改写内容"（如自动加标签、裁剪标题）的情形——它只保证**提交时**是对的。
- 型号不写死意味着文档在这一点上**故意保持不确定**；实现时必须提供配置项与默认值，否则会变成"没人知道该填什么"。
- 简报的手动关闭使"已读"成为一个显式状态，但也意味着若本人长期不关闭，issue 会堆积；看守只看当日，因此堆积不影响告警功能。
