# 先在本地验证再部署服务器：角色划分、环境分支与验证顺序

## Context

部署节奏确定为**先在本地验证，经本人确认后再部署服务器**。这修正了此前的若干前提——ADR-0009/0023 的部署形态、ADR-0018 的写入者假设、ADR-0022 的代理规则——都是在"直接上服务器"这一前提下写的。

同时核实了本地与服务器的实际差异：

| | 本地（macOS） | 服务器（阿里云 ECS） |
|---|---|---|
| 架构 / 内存 | arm64 / **16GB** | x86 / **2GB** |
| 代理 | Clash Verge GUI（`verge-mihomo` 内核），已运行 | 需装 mihomo 内核 + systemd |
| 显示器 | 真实桌面 | 无（需 Xvfb） |
| Python | 3.9.6（偏旧，可用 `uv` 管理） | Alibaba Cloud Linux |
| 工具 | node/npm/pnpm/uv 齐备；gh、docker 未装 | 待部署 |

**16GB 与 2GB 的差距是本决定最关键的后果**：本地不会有 OOM，因此**本地验证通过并不能证明服务器上不会 OOM**。ADR-0023 的内存防御（按需启动 Chrome、内存约束参数、发布前内存预检）在本地几乎是空跑的，必须在服务器上单独验证。

## Decision

**一、验证顺序：先外部依赖，再自建部分。** 三个外部依赖（`wewrite` / `toutiao-ops` / `Agent-Reach`）都是别人写的，可能直接跑不起来。先撞这些墙，再写自建的采集/分拣——否则自建部分的接口可能白设计。前置资产（风格访谈 + 种子卡）按 Q63 与 Q152 的合并结果处理：属于外部依赖验证之后的紧接步骤，因为它是后续所有阶段质量验证的前提。

**二、本地允许真发布，但只发 1–2 篇。** 目的是验证**发布链路**（填表、读回校验、反查验证、熔断、教学副本），不是验证内容质量。本地是住宅 IP + 真实桌面，风控风险远低于服务器。发多了不必要地占用账号，且 ADR-0017 已定系统不自动删改已发布内容。

**三、服务器先 dry-run 验证，再开真发。** 服务器特有的风险（OOM、Xvfb、mihomo 分流、git 同步）必须在真发前压出来，因为本地 16GB 压不出内存问题。

**四、角色划分：验证期只跑本地；上线后只跑服务器。** 这是本 ADR 最重要的一条。ADR-0018 的所有权表假设**只有一个系统写入者**；若本地与服务器同时跑完整流水线并写仓，可能出现同日发两篇或对同一事件重复发文——而"批量发布重复内容"是头条社区规范明令禁止的行为（ADR-0001 已记录）。因此切换主环境时必须停掉另一个的自动发布。不用锁文件机制：靠纪律即可，但切换是一次需要显式执行的动作。

**五、Chrome 按环境分支。** 本地用有头 Chrome（真实桌面，无需 Xvfb）；服务器用 Xvfb + 内存约束参数。该差异作为一个配置项，不硬编码。理由：本地套 Xvfb 反而多一层且不是真实环境，而首次登录需要扫码看窗口。

**六、本地先手动触发，验证后再接定时任务。** 调试阶段手动最快，且定时任务在本地开着容易忘记关——这会与第四条的角色划分风险叠加。

**七、本地与服务器共用同一个私有仓。** 认知资产、风格、教学副本、简报都在仓内，通过 git 同步。这不是选择而是必然：ADR-0026 的风格学习依赖"你在本地改完 push、系统 pull"，若两边各一套资产，沉淀循环会直接断裂。

## 事实修正

**代理客户端是 Clash Verge，不是 FlClash。** 本机运行的是 `Clash Verge.app` + `verge-mihomo` 内核（`~/.config/clash/` 与 `~/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev/`）。结论不变（桌面 GUI 客户端；服务器仍应跑裸 mihomo 内核 + systemd），但此前文档中的"FlClash"应更正。

**头条分流规则已由机场订阅内置。** 核实当前订阅 profile 后发现已包含完整的头条域名族分流，全部指向"🎯 国内流量"：

```
DOMAIN-SUFFIX,toutiao.com
DOMAIN-SUFFIX,toutiaocdn.com / toutiaocdn.net
DOMAIN-SUFFIX,toutiaoapi.com
DOMAIN-SUFFIX,toutiaohao.com / toutiaohao.net
DOMAIN-SUFFIX,toutiaoimg.com
DOMAIN-SUFFIX,toutiaocloud.com
DOMAIN-SUFFIX,toutiao13.com
```

这使 ADR-0022 的核心要求从"必须自己写规则"变为"**验证既有规则确实生效**"。而且该域名族比手写的更完整。因此 ADR-0022 的规则应作为**兜底**保留，而非唯一手段。

## Consequences

- **本地验证的覆盖面有明确边界**：它验证逻辑正确性与链路连通性，但**不验证**内存约束、Xvfb 行为、以及代理内核在 systemd 下的稳定性。这些属服务器专属验证，不能被本地的成功所替代。
- 角色切换（本地 → 服务器）是一次**不可自动化的人工动作**，且漏做会导致重复发文。因此它应写入上线清单，并在切换后通过简报确认当日只有一次发布。
- 共用仓意味着**本地调试产生的提交会与将来的服务器提交混在同一历史里**。验证期的脏数据（测试卡、试发文章）会留在资产中。若这与"资产洁净"冲突，需在切换时做一次清理提交——但注意 `outputs/` 的历史不可重写（ADR-0026 的发布快照依赖）。
- 本地 Python 3.9.6 偏旧，而 `wewrite` 与 `Agent-Reach` 可能需要更新的版本。用 `uv` 隔离环境可解决，但这也意味着**本地与服务器的 Python 版本可能不同**，是又一处环境差异，不可假设一致。
- 真发 1–2 篇的策略意味着**发布链路的偶发问题（选择器边界、封面模式、反查时序）可能未被覆盖**。这是为节省账号占用而接受的覆盖率损失。
