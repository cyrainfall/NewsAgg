# 移植 ybrain 方法但丢弃 IMA 后端，并补一个机器分拣层

## Context

用户要求"过程参考技能 ybrain，但资料不用 ima"。

对 ybrain 的完整拆解显示，它的方法与它的后端是可以分离的。方法部分（CODE 四段循环、PARA 五文件夹、知识包=只追加的活文档、捕获阶段禁止分类/组织阶段唯一分类的不对称、先捕获后分类）是纯粹的工程模式；而后端耦合被收敛在单一点上——全部 IMA 调用都经过 `scripts/ima_api.cjs <apiPath> <json-body>`，硬规则明令禁止绕过它直接构造请求。因此换后端是写一个保持该契约的 shim，不是重写。

但拆解同时暴露了一个缺口：**ybrain 没有任何机器分拣层**，而且是刻意的——捕获阶段禁止四问筛选，组织阶段是唯一分类点且由人执行。用户的需求恰好相反：无人值守的新闻流水线必须自己判断"什么值得写"，没有人会在循环里逐条分拣。

## Decision

移植 ybrain 的方法骨架，丢弃其 IMA 后端与后端特有的约束，并新增一个 ybrain 刻意不做的阶段：机器分拣。

具体地：

- **保留**：只追加不重建的活文档（观点卡）、双通道收件箱、先捕获后分类的不对称、以标题前缀作类型系统、写后读回校验、来源可追溯但不暴露内部 ID。
- **替换**：`ima_api.cjs` 及其全部 `openapi/*` 端点、COS 预签名上传、凭证文件与环境变量。后端改为文件 + git。
- **新增**：选题信号（事件聚簇 + 推荐理由 + 置信度）与取舍判定（跳过/续写/新写）。这两者 ybrain 没有对应物。
- **修正**：ybrain 的"长专注/短专注"只是一行魔法字符串约定（`可用于：项目 X`），过于单薄；本系统以"观点卡 + 取舍判定"承担同样的汇聚职能，不再沿用该字符串约定。

## Consequences

- 换后端成本低（shim + 语义适配），但 IMA 的**服务端语义检索**没有对应物：文件后端必须自己提供检索（先用 grep/文件名约定，检索真成瓶颈再考虑嵌入）。这直接影响"唤起"与"表达"两个阶段。
- IMA 的"无删除 API"约束消失，文件后端应当提供真正的归档/删除，顺带取消了 ybrain 用 `4-存档` 当垃圾桶的权宜之计。
- 新增的机器分拣层是本项目真正的工程增量，也是最容易做错的部分：它必须有置信度且允许弃权，否则会把"不确定"伪装成"已判定"。
- `.agents/skills/` 中现有的 `ybrain*` 技能保持原样不动，作为参考实现而非本项目的运行组件。
