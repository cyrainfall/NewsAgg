# 发布包装层实测：dry-run 会真的建草稿，且草稿无法被 content list 反查

## Context

按 ADR-0024 / ADR-0014 实现发布包装层（`newsagg-publish`），并以 dry-run 走通全链路。实测暴露两个直接影响 ADR-0024 反查验证设计的事实。

## 实测发现

### 一、dry-run（`--draft`）会在真实账号上创建真实草稿

包装层用 `toutiao-ops publish article --draft` 实现"停在发布前"。实测通过：`auth check` → 填表 → 存草稿，退出码 0。

但这意味着 **dry-run 不是零副作用**：它在本人头条账号上留下了一条真实草稿（标题为测试串）。ADR-0014 把 dry-run 描述为"走到填完表单、停在发布按钮前"——**实际实现比这更靠后一步**：内容已经落库为草稿，只是未公开发布。因此：

- dry-run 在账号上**累积垃圾草稿**，需人工到 `mp.toutiao.com` 草稿箱清理。
- 它并非"无痕验证"，而是"不公开的验证"。

### 二、草稿无法通过 `content list` 反查

`content list --status` 只接受三个值：

```
--status <status>  状态: published / reviewing / rejected  (default: "published")
```

**没有 `draft`**。实测 `--status all` 也不返回草稿（该值不在枚举内，静默按默认处理）。因此：

- 反查验证（ADR-0024）**只能验证已发布/审核中/被拒的作品，无法验证草稿**。
- dry-run 路径**没有可用的自动验证手段**——它成功了也只能从退出码判断，而 JSON 返回值不可信（ADR-0024）。这是 dry-run 与真发之间的一个能力缺口。

### 三、`content list` 的返回是两层嵌套，且实为原始 API 信封

返回 `items` 是**多个原始 API 响应**的数组，而非扁平作品列表：

```
items[0] = {data: [], errno: 20100, total_number: 0, login_status: 1, ...}   ← 空/入口
items[1] = {error_code: 0, data: {msg_list: [...], read_cursor: ...}}        ← 真实作品在此
```

真实作品在 `items[?].data.msg_list` 内。ADR-0030 已记录"返回原始 API 信封而非扁平结构"，此处进一步确认了**具体路径**：反查逻辑必须遍历 `items[*].data.msg_list[*].title`，不能假设顶层有 `items[].title`。

## Decision

**一、dry-run 的语义修正为"创建草稿（不公开）"**，并明确它会在账号上留痕。因此：
- dry-run 的用途是**验证选择器与表单流程**，不是"无副作用的演练"。
- 每次 dry-run 后需人工清理草稿；包装层应在输出中提示这一点。

**二、反查验证只用于真发路径，dry-run 不做反查**（因为草稿查不到）。dry-run 的判定依据是**退出码**，并在输出中标注"草稿已创建，需人工确认与清理"。

**三、反查路径固定为 `items[*].data.msg_list[*]`**，并在实现中容错（结构变化时报告解析失败而非静默判定"未找到"——静默判定会导致误判为"未发出"从而诱使重发，而重发是重复发文的成因）。

**四、标题长度门的上限校验按字符数**（实测 27 字通过，符合 2~30 的要求）。

## Consequences

- **dry-run 的副作用使其不能密集使用**：每验证一次就在账号上留一条草稿。这削弱了 ADR-0014"验证通过才开真发"的迭代效率——验证本身有成本。
- **"发布成功"的判定完全落在反查上，而反查看不到草稿**，因此真发路径的反查是唯一可靠判据；这也意味着若平台在某次发布后**长时间不把作品放进 `msg_list`**（如延迟入库），反查会误判为"未发出"。ADR-0011 已规定此种情形"不重发、走核实"，因此后果是**当日不发文**，而非重复发文——失败方向是安全的。
- `msg_list` 为空（新账号无作品时）是**正常状态**，不是错误。反查逻辑必须区分"列表为空"与"解析失败"。
- 包装层已验证的安全门：熔断状态拦截、成稿存在性、标题长度 2~30、封面必填、内存预检、登录预检（3 次重试 + 仅登录失效才熔断）、串行文件锁。这些在真实调用中均按预期工作。
