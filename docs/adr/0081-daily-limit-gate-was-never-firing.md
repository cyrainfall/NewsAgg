# 「每日 1 篇」的闸一直在空转，且阅读率会算出 120%

## Context

2026-10-28 21:00 的主流程第一次在 4 条定时任务重建后真实运行（ADR-0080）。第 1 段
跑通，采集 282 条 / 预筛 156 条 / 分拣输入包组装完成。值此之际顺手核对了
`publish.py` 的「每日 1 篇」闸门——**这是一次计划外的发现**，但它是本轮最重要的事。

## 发现

### 一、`repo_root_of()` 上溯三级，导致「每日 1 篇」从 ADR-0074 起一直没生效

`publish.py:405` 的文档字符串写得很清楚：

> 账本路径固定是 `<root>/.newsagg/publish-ledger.jsonl`，所以上溯两级就是根。

代码写的是：

```python
return Path(ledger_path).resolve().parent.parent.parent   # 三级
```

于是 `count_published_today()` 里的 `read_merged(repo_root_of(ledger))` 去找
`<仓库父目录>/.newsagg/publish-ledger.jsonl` 与 `<仓库父目录>/reports/publish-ledger.jsonl`
——**两个都不存在**，`read_records()` 对不存在的路径返回 `[]`（那是它的容错设计，
见 `publish_ledger.read_records`），合并结果恒为空，`count_published_today()` **永远返回 `[]`**。

实测（2026-10-28）：

```
ledger 实际位置 : C:\...\repository_git\NewsAgg\.newsagg\publish-ledger.jsonl
代码算出的 root : C:\...\repository_git        <-- 多了一级
真实 root       : C:\...\repository_git\NewsAgg
count_published_today("2026-10-27") -> []
count_published_today("2026-10-28") -> []      <-- 明明刚发过一篇
```

修好之后同一条命令返回 `1 篇`（10-27 那篇是 10-28 00:44 发的）。

**这不是「少拦了一次」，是这道闸从落地起一次都没拦过。** 而它的两份文档都写得很清楚
（ADR-0014 定参数、ADR-0059 加闸门），说明**判据从来不是缺的，缺的是有东西在跑它**
——ADR-0057 的同一条判据（"测试只存在于有东西跑它的时候"）。

`grep count_published_today tests/` 当时**零命中**。ADR-0059 为此专门写了一整节
"「每日 1 篇」必须在脚本层有闸"，并加了 `--allow-daily-override` 与门 0.5，
却没给它一个测试。那次误发（真发了一篇重复文章）就发生在这道"存在"的闸旁边。

### 二、阅读率会算出 120%，并原样印进简报

10-27 那篇次日读回时是 `showCount=5 / readCount=6`——**阅读数大于展现数**。两条计数
不同步（平台先记点击、后补展现），于是 `read / show = 1.2`。

这个值从两条路上造成损害：

1. **进基准中位数。** `evaluate()` 的基线取最近 N 篇 `read_rate` 的中位数，一个 1.2
   会把阈值抬高 → **该降频时降不下来**。而自动降频是本系统唯一的行为调节器（ADR-0010）。
2. **被简报原样印出。** `brief.py:494` 直接 `fmt_rate(read_rate)`，读者会看到
   「阅读率 120%」。简报的信噪比是它唯一的资产（ADR-0055），一个明显不可能的数字
   会让人开始怀疑同一段里的其他数字。

## Decision

1. **`repo_root_of()` 改为 `parent.parent`**，并把这段公案写进函数文档——下一个
   读它的人需要知道为什么这里有一大段注释却只有一行代码。
2. **补 `DailyLimitGateTest`（3 个用例）**：`repo_root_of` 必须真的指回仓库根；
   今天真发的必须被数到；dry-run 草稿与 `accidental` 误发不占额度。
   **并做反向验证**：把代码改回三级，测试立刻变红。
3. **阅读率 `> 1` 视为窗口期未同步，记 `None`**（与「展现为 0」同类：此刻算不出
   有意义的比率），原始 `showCount`/`readCount` 仍留在 `metrics` 里供人看。
   两条路径（浏览器 `extract_articles` / 纯 HTTP `fetch_content_list_api`）同口径。
4. **补 `TestReadRateClamp`（3 个用例）**：5/6 → `None`；正常比率不受影响；
   恰好 100% 保留（合法边界）。同样反向验证。
5. **本轮照闸门走，今天不真发。** 用户已确认：把分拣与写作跑完，成稿留在
   `outputs/`，明日处理。prompt 明确禁止自行 `--allow-daily-override`（ADR-0059
   的教训），所以这个选择必须由人做——**闸门第一次生效就立刻改变了当天的行为**。

## Consequences

- **今晚这次运行的性质变了**：它不再是"发了什么"，而是"闸门第一次说不行"。
  产出是一篇待处理成稿 + 一份写明原因的简报，而不是一篇已发布文章。
- **闸门现在真的会拦**。这意味着从今天起，跨零点运行会**吃掉次日额度**：
  21:00 的主流程若跑到 00:00 之后才发布，那篇算次日。ADR-0014 按日历日计，
  这个行为是对的，但它会以"第二天不能发"的形式让人困惑。今天就是第一次。
  可能的改进方向（未采纳）：把额度判据改成按 **slug 的内容日** 而非发布时刻，
  但那要同时改 ADR-0014 的措辞，且会让"跨零点重跑"变得可以重复发文——**风险更高**，
  所以今天维持日历日。
- **`count_published_today` 此前是纯粹的装饰**。这个事实会让 ADR-0059 那次的结论
  更强而不是更弱：它当时论证的是"约定不等于闸门"，而事后证明**连闸门都可能是空的**。
  判据要从"有没有闸"升级成"有没有东西在跑这个闸"。
- **ADR-0080 记的 ② b 表现读回"必然回落 browser"仍然成立**，但今天多了一条：
  回落之后拿到的数据也被印歪了（120%）。两条都指向同一个主题——**无人值守时
  没人去看这些数字，所以数字错了也不会有人当场发现**。
