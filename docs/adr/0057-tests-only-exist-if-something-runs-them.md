# 测试只有跑起来才算存在，而「跑起来」不能依赖人的记忆

## Context

ADR-0056 落码时，本仓库第一次有了测试文件（`tests/`，标准库 `unittest`，32 个用例）。
但在落码过程中确认了一件更基础的事：**在此之前，这个仓库一个测试文件都没有**。

`git log --all --diff-filter=D -- '*test*'` 零命中——不是「测试被删了」，是从来没存在过。
唯一的例外是 ADR-0043 的「验证方式」段落，它声称当时跑过「阈值表与六个场景」的单元测试，
但那些测试**没有提交**：它们存在过的唯一证据，是一份自然语言写下的声明。

这个缺口不是疏忽，而是这套系统的形状决定的。ADR-0025 把判断交给 agent、把确定性交给脚本；
脚本里那些真正会静默出错的地方（位次归一、观测合并、字段重建），恰好是**没有人会手工验第二遍**的部分。
ADR-0042（三份 `parse_frontmatter` 漂移）、ADR-0043（存量 `hot` 字符串留在轨迹里）、
ADR-0054（字段名漂移只让简报少显示一行、退出码仍是 0）都是同一形态：
**缺陷以「历史数据」或「少显示一行」的形态存活，而没有任何东西会去检查它。**

ADR-0056 落码时，测试确实抓到了四个 bug（两个实现错、两个设计错）。但那四个 bug 能被抓到，
靠的是我在落码当天**恰好想起来跑了一遍**。下一次改动不会有这个保证。

## 发现

### 一、「有测试文件」与「测试在跑」是两件事

落码后我先确认了一件容易忽略的事：从**仓库根**跑 `python3 -m unittest discover`，
在 `tests/` 没有 `__init__.py` 时会**静默发现 0 个测试并打印 `OK`**，退出码 0。

```
$ mv tests/__init__.py /tmp/ && python3 -m unittest discover -v
----------------------------------------------------------------------
Ran 0 tests in 0.000s

OK
$ echo $?
0
```

这是本仓库已经记录过三次的失败形状的第四次实例：`catch {}` 吞掉失败（ADR-0047）、
`kept_new is None` 印成 `?`（ADR-0042）、失效源不进简报（ADR-0047）。
它们的共性不是「代码写错了」，而是**代码假装自己做完了**。
一个返回 0 的「跑了 0 个测试」，比一条红色失败更危险：它占据的是「已验证」这个位置。

### 二、只判退出码不够，必须判「跑了几个」

上面那次实验说明：`unittest discover` 在什么都没发现时**退出码也是 0**。
所以 CI 里只写 `python3 -m unittest discover` 是不够的——它在测试被移走、改名、
或者 `__init__.py` 被误删之后，会继续绿着。

要挡住这个，判据必须来自**产出物本身**（这是 ADR-0044 发现六、七的纪律：
自检不能复述设计意图，必须读实际产出）。`unittest` 会把实际跑了多少条打在
`Ran N tests` 这行上，所以判据就是这一行里的 N：

```
RAN=$(grep -oE '^Ran [0-9]+ test' /tmp/unittest.log | grep -oE '[0-9]+' || echo 0)
if [ "${RAN:-0}" -lt 1 ]; then exit 1; fi
```

实测这个守卫**真的会响**：把 `__init__.py` 移走后，`RAN=0`，守卫退出 1。
不是「看起来合理」，是验证过它会拦。

### 三、`| tee` 会掩码退出码，而 `pipefail` 的顺序有讲究

CI 里要把测试输出留在日志里，就得 `| tee`。而这正是 ADR-0028 记录过的陷阱：
**命令成功与否一律看退出码，不经管道——管道会掩码退出码。**

实测（干净 shell，一个故意失败的测试）：

```
$ bash -c 'python3 -m unittest discover 2>&1 | tee /tmp/f.log >/dev/null; echo $?'
0                                        # ← 测试失败了，但退出码是 0
$ bash -c 'set -o pipefail; python3 -m unittest discover 2>&1 | tee /tmp/f.log >/dev/null; echo $?'
1                                        # ← 正确
```

所以 `set -euo pipefail` 必须出现在 `| tee` 之前。工作流里它是每个 step 的第一行。

### 四、两个解释器都在生产路径上，只测一个等于只保护一半

`run_all.sh` 用**裸 `python3`** 调绝大多数脚本（服务器上是 3.9），
而封面与取图步骤钉的是 `COVER_PY=.uv-tools/wewrite/bin/python`（3.12，ADR-0039/0052）。
两个版本都是生产路径。

3.9 是**下限**，这一档尤其重要：开发机上跑 3.12 不会报错的语法（运行期求值的 `X | None`、
`match`），在服务器上直接崩。而这类错误只在部署时才现形——那时已经在无人值守的链路里了。
所以 CI 用矩阵跑 `["3.9", "3.12"]`，`fail-fast: false`（两个版本各自给结论，不要因为
3.9 挂了就不看 3.12）。

### 五、单元测试只覆盖被 import 的那几个函数，其余部分仍需一层「还能编译」

`tests/` 里 32 个用例只碰了 `collect.py` 的归一化/合并、`triage.py` 的趋势计算、
`brief.py` 的渲染。脚本里其余部分——参数解析、落盘路径、`run_all.sh` 的 bash 分支——
没有任何测试。这些部分挡不住逻辑错，但至少每次变更都能确认「还能编译、还是合法 bash」，
这挡得住「改完就崩」这一类。

语法检查刻意用 **3.9**（下限版本）做：能在 3.9 上编译，才可能在服务器上跑。

## Decision

1. **测试的唯一消费者是 CI，不是人的记忆。** 新增 `.github/workflows/newsagg-tests.yml`，
   在 `push` 到 `main`、任何 `pull_request`、以及手动 `workflow_dispatch` 时运行
   `python3 -m unittest discover`。理由：一份没人跑的测试与没有测试等价，而且更糟——
   它让人以为有回归保护。这与 ADR-0038 的 `hot_history`（记了三天没人读）是同一形态，
   区别只在这次的「消费者」是自动化的。

2. **CI 必须断言「跑了至少一个测试」，不能只判退出码。** 因为 `discover` 在发现 0 个
   测试时退出码也是 0（发现一）。判据取 `Ran N tests` 里的 N，而不是复述「我们配了
   discover」这个意图（ADR-0044 发现六/七的纪律）。同理，`tests/` 下 `test_*.py`
   的数量也单独断言一次——`__init__.py` 单独存在就能让目录非空。

3. **矩阵跑 3.9 与 3.12，`fail-fast: false`。** 两者都在生产路径上（裸 `python3` 与
   `COVER_PY`）；3.9 是下限，只有它才能挡住「开发机过了、服务器崩」的语法。
   两个版本各自给结论，一个挂了不影响另一个的诊断。

4. **`set -euo pipefail` 必须先于任何 `| tee`。** ADR-0028 的纪律在 CI 里同样适用：
   管道掩码退出码，实测失败测试经 `| tee` 后退出码为 0。这一条不是「记得写」，
   是工作流里每个 step 的第一行。

5. **静态检查与单元测试分开成两个 job。** 单元测试给「逻辑对不对」，静态检查给
   「还能不能跑」。合成一个 job 时，语法错会让测试 job 直接失败在更早的步骤上，
   看起来像「测试挂了」；分开后失败的位置就说明问题在哪一层。静态检查覆盖
   `.agents/skills/*/newsagg-*/scripts/*.py` 的 `py_compile` 与 `run_all.sh` 的 `bash -n`。

6. **本工作流与看守分工明确，不合并。** 看守（`newsagg-watchdog.yml`）跑 cron、
   判「主系统整体是否还活着」（简报存在 + 五段齐备）；本工作流跑代码变更、判
   「这次改动有没有弄坏确定性逻辑」。两者都跑在 GitHub 的机器上，但触发条件与
   判据完全不同——合并会让「代码改坏了」与「系统没跑」混成同一个信号。

## Consequences

- **CI 只保护确定性部分。** 32 个用例覆盖的是归一化、合并、趋势、渲染；而本项目
  大量逻辑是 agent 判断（分拣、写作、封面论据选择），那些部分 CI 一条都测不到。
  这不改变 DESIGN.md 里「越靠近内容好坏，机器越验不了」的既有结论（残余风险 25/40），
  但至少把「确定性部分」从「完全无保护」提到了「有回归线」。

- **测试会随数据格式变更而过期，且不报错。** ADR-0042/0043/0056 都改过数据形状；
  每次改都要同步改测试夹具。若只改了生产者没改夹具，测试会**继续绿**（因为夹具
  里是旧形状），而真实数据走的是新形状——这是残余风险 24（修格式漏掉存量数据）的
  测试侧变体。缓解只能是「改格式时同时看夹具」，没有机制强制。

- **CI 跑在 GitHub 的机器上，与生产环境不同。** 它没有 `.newsagg/`（不入库）、
  没有 `.uv-tools/`、没有 Chrome、没有热榜服务。所以它能验的只有「纯函数」与「语法」。
  实测确认过这一点：全新 clone（无 `.newsagg/`）上 32 个测试全部通过——这既是
  「测试不依赖运行时状态」的证据，也是「CI 验不到运行时行为」的边界。

- **多了一处需要手工同步的自然语言。** 新增测试后，`DESIGN.md` 的落地顺序与
  `WALKTHROUGH.md` 都该提到「改完跑 `python3 -m unittest discover`」。漏一处，
  下一个人就只知道改代码、不知道有测试。这与残余风险 41（赛道有四个副本）同型，
  是自然语言文档的固有代价。

- **`3.9` 这个下限本身会过期。** GitHub Actions 的 `ubuntu-latest` 上 `setup-python`
  仍支持 3.9，但上游迟早会弃用。届时矩阵里的 3.9 会开始装不上，而这个失败
  **看起来像代码坏了**。缓解是这一行写在矩阵里显眼处，且失败信息会直接指出
  「安装 Python 3.9 失败」——那时该做的是决定「升下限」还是「换 runner」，
  而不是改测试。
