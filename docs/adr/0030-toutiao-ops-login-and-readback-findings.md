# toutiao-ops 登录与数据读回实测：会话持久化、并发锁与返回值形状

## Context

按 ADR-0027 阶段 0，实际完成首次扫码登录（Q84）并验证数据读回（Q41）。实测暴露了三条此前未记录的接口约束，其中一条会直接影响无人值守的可靠性。

## 实测结果

**登录成功**：账号 `淆雨学学`（`userId 111091683370`），扫码流程分两阶段输出（`waiting_for_scan` → `logged_in: true`），二维码每约 50 秒自动刷新，共 6 次（约 5 分钟窗口），截图落在 `$HOME/.toutiao-ops/accounts/default/screenshots/`。

**会话跨进程持久化**：新进程执行 `auth check` 返回 `logged_in: true`，证明会话写入了持久化 profile（`browser-data/`，约 100MB）。这满足 Q84，并使 Q66 的发布前预检（`auth check`）可用。

**`content list` 可用**：返回 `success: true`、`source: api_intercept`、`login_status: 1`。新账号无作品，故 `data: []`、`total_number: 0`——是正确结果，不是故障。

### 一、同一账号的浏览器命令**不能并发**

实测中我同时启动了 `content list` 与 `analytics works`，后者失败：

```
browserType.launchPersistentContext: Target page, context or browser has been closed
[pid=79674][out] 正在现有的浏览器会话中打开。
<process did exit: exitCode=0>
```

原因：两个进程争抢同一个 `user-data-dir`（`browser-data/`）。SKILL.md 已明确警告"不要对同一个账号同时运行多个命令（会争抢浏览器上下文锁文件）"，实测证实。

**关键后果**：失败表现为 **Playwright 抛出异常**（退出码 1），但它是一个**瞬时竞态**，重试即可成功——这使它容易被误判为"选择器失效"或"平台拒绝"，从而触发不必要的熔断。**必须先串行化，再谈熔断。**

### 二、`analytics works` 的返回值混入了 DOM 噪声

`analytics works --type article` 返回的 `metrics` 对象把真实指标与**省份名**混在一起：

```json
{"metrics":{"昨日展现量":"0","昨日阅读量":"0","昨日点赞量":"0","昨日评论量":"0",
            "上海":"0","云南":"0","内蒙古":"0","北京":"0", ...}}
```

`source` 字段为 `dom_scrape`（而非 `api_intercept`），说明它回退到了 DOM 抓取，并把地域分布面板的省份当成了指标键。**这是上游的数据质量缺陷**，本项目的表现数据回路（ADR-0026 循环 C / ADR-0010）不能直接消费该字段，必须按已知指标名白名单提取。

### 三、`content list` 返回原始 API 信封，不是扁平化结果

返回结构是头条的原始响应（含 `errno`、`login_status`、`tips`、`api_base_info` 等），作品列表在嵌套字段中，而非顶层 `items[]`。ADR-0029 已记录采集层存在两种形状需归一化，此处**第三个形状**同样需要归一化。

## Decision

**一、浏览器类命令必须串行执行**，同一账号同一时刻只允许一个 `toutiao-ops` 进程。实现方式：调用包装层加一把**文件锁**（锁文件落在仓内，如 `.newsagg/browser.lock`），拿不到锁则等待或跳过本轮，而**不视为失败**。

**二、区分"并发冲突"与"真实失败"**：包装层在捕获到 `Target page, context or browser has been closed` 或"正在现有的浏览器会话中打开"时，判定为**并发冲突**，走重试（等锁释放）而非熔断。这是对 ADR-0011"两类重试"的补充：**只读探测可重试**的判据需要加上"且失败原因是并发冲突"。

**三、表现数据按白名单提取**，不信任 `metrics` 的全量键。已知指标（`昨日展现量`/`昨日阅读量`/`昨日点赞量`/`昨日评论量` 等）显式列出，其余键（省份、机型等分布数据）单独归类或忽略。

**四、`content list` 的结果需归一化**后再用于 ADR-0024 的反查验证（比对标题）。反查逻辑不能假设顶层有扁平的 `items[].title`。

**五、`$HOME` 重定向是所有这些命令的前置条件**（见 ADR-0028）。

## Consequences

- **串行化把"并发"从可靠性问题变成吞吐问题**：一轮发布流程内，登录预检、填表、读回、反查、表现数据回读都必须排队。每次启动 Chrome 有秒级开销，因此一轮完整流程的耗时由"串行步数 × 单步耗时"决定。这对无人值守是可接受的（当晚发布，无延迟要求），但对调试是明显负担。
- **锁机制本身成为新的失败点**：若进程崩溃后锁文件未释放，后续所有浏览器操作会被无限阻塞。因此锁必须有超时与陈旧检测（按进程存活判断），而不能是纯文件存在性检查。
- `analytics` 的数据质量缺陷意味着**表现数据回路（循环 C）在源头就不可靠**。ADR-0010 已把它定为"软信号"，这一发现强化了该决定的正确性——连硬指标都混着省份名，更不该据此做硬决策。
- 三个不同的返回值形状（DailyHotApi 的 `id`/`title`、原始接口的 `ClusterId`/`Title`、`content list` 的 API 信封）都必须归一化。若在代码中混用，会在切换路径时产生静默错误——与 ADR-0029 的同类风险。
- 本次实测再次证明 **"先撞墙"策略的价值**：这三条约束在写代码前都不明显，而它们直接决定了包装层的形状（锁、错误分类、白名单、归一化）。
