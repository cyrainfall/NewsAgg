# 「决定保留」不等于「已经删除」，账本不能把两种终态混成一种

## Context

ADR-0047 修掉了「一次发布动作多发一条微头条」的根因，但已经发出去的两条删不掉
（`toutiao-ops` 没有删除能力）。系统当时的处理是：账本记 `weitoutiao_leak`，
简报 ⑤ 段**每天**把它们列出来，直到人在账本记录上写 `leak_resolved_at` 为止。

这个设计默认了「终态只有一种：删掉」。2026-10-22 用户看完简报后说（m18349）：

> 两条 10-14 / 10-18 的微头条保留即可

——即**决定保留**，不删。于是出现了原设计没考虑的状态：既没有删，也不该再提醒。

## 发现

### 一、提醒没有「接受」这个出口，只有「解决」

`brief.py` 的过滤条件是「有 `weitoutiao_leak` 且没有 `leak_resolved_at`」。
要让提醒停下，唯一写法是在账本上写 `leak_resolved_at`——而那个字段的名字和
含义都是「已删除」。用它标记「决定保留」，等于让账本说一句假话。

代价不是美观问题：**账本是复盘时唯一的事实来源**（ADR-0051 之后它还记着平台实际
标题、gid、更正痕迹）。如果它把「保留」记成「删除」，那么半年后回看时，没人能
分辨这两条微头条到底还在不在平台上。ADR-0029 已经确立过同一条纪律——账本可以
被人工更正，但必须留下痕迹、不覆盖原始判据。用错字段名，就是一次没有痕迹的覆盖。

### 二、另一个方向的错法：把「保留」做成换措辞的唠叨

如果只是改文案（把「需要你手工删除」改成「已按你的决定保留」）但**仍然每天出现**，
提醒就变成了另一种形式的噪音：用户要的是这件事消失，不是换一句话继续说。
每日简报的信噪比是它唯一的资产——一旦 ⑤ 段每天挂着两条已经决定过的事，
下一次真正需要介入的事就会被一起略过。

### 三、提醒的生命周期应该有三个终态，不是一个

- **未处理**：什么都没写 → 每天列出（现状，正确）
- **已删除**：写 `leak_resolved_at` → 停止
- **已接受保留**：写 `leak_accepted_at` → 停止，但**在做决定的那天确认一次**，
  之后不再出现

第三个终态的「确认一次」不是多余的：用户做决定时看到的是「已按你的决定保留」，
而不是一句都没有——后者会让人怀疑自己的指令是否生效。

## Decision

1. **新增 `leak_accepted_at` 字段**，与 `leak_resolved_at` 并列，语义互斥：
   前者 = 人决定保留，后者 = 人删掉了。两者任一存在，提醒即停止。
2. **不再用 `leak_resolved_at` 表达「保留」。** 已经这么写过的记录若出现，
   按语义纠正回 `leak_accepted_at` 并附 `leak_accepted_note`（本次两条即如此处理，
   note 里记下用户原话）。
3. **「已接受」只在做决定当天在简报里确认一次**，靠 `leak_accepted_at` 的日期
   与简报日期相等来判定。次日及以后完全不出现。
4. **简报文案写清两个出口**，不再只提「删完加 `leak_resolved_at`」——
   因为「我决定不删」是同样合法、且更可能发生的选择。
5. **保留 ADR-0047 的检测与记账不变。** 这条 ADR 只改「提醒如何结束」，
   不改「泄漏如何被发现」；根因修复（先读状态、只在该取消时点、点后读回验证）
   仍然有效，新泄漏仍会照常出现。
6. **「已接受」的确认块与「未处理」的提醒块是两个独立判断，不是 if/else。**
   第一版把它写在 `else` 里，于是「同一天既有刚决定保留的、又有还没人处理的」
   时，前者会静默消失。用三条构造记录（未处理 / 当天接受 / 已删除）跑
   `section_actions()` 才发现：接受确认只在 `leaks` 为空时出现。
   改成并列判断后：未处理的天天出现、当天接受的只在当天出现、已删除的永不出现。

## Consequences

- **账本多了一个字段，但少了一次说谎的机会。** 复盘时「这两条还在平台上，是本人
  决定保留的」是可读的，而不是需要靠记忆还原。
- **`leak_accepted_at` 与 `leak_resolved_at` 都是人的手写字段**，系统不提供 CLI
  去改它们（`.newsagg/` 本就在 `.gitignore` 内、不入库）。这意味着：换机器、
  重装、或误删 `.newsagg/` 之后，两个终态都会丢失，提醒会重新出现。
  缓解是 `.newsagg/publish-ledger.jsonl` 值得单独备份——但当前没有做。
- **「接受」是一个不可撤销的静默。** 写了 `leak_accepted_at` 之后，系统再也不提
  这两条微头条，哪怕它们半年后仍然挂在平台上。这是有意的：提醒的价值在于
  「提醒你做决定」，不在于「替你记住决定」。
- **新增一个需要同步的地方。** 简报文案、`DESIGN.md` 残余风险 31、`SKILL.md` 的
  微头条小节都要提到两个字段；漏掉任何一处，下一个人就只会知道「删除」这一个出口。
  这与残余风险 41（赛道有四个自然语言副本）同型，是自然语言文档的固有代价。
- **它暴露了一类更普遍的问题**：凡是「提醒直到你处理」的机制，都隐含假设
  「处理 = 消除」。真实的终态常常包括「处理 = 接受它存在」。下次设计任何
  「持续提醒」时，先问一句：**接受算不算处理完？**
