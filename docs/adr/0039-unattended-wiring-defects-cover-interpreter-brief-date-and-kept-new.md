# ADR-0039：无人值守接线实测发现的三处缺陷——封面解释器、选题包日期、采集新增数

## Context

ADR-0038 把 `run_all.sh` 补成真正的九步编排、切成三段交接，并把看守改为读仓库里的
`reports/<日期>.md`。落地之后必须真的**按三段跑一遍**才能知道它是否无人值守——
本次实测（`--collect-only` / `--no-collect` / `--after-triage` / `--after-write`，
含 dry-run 与真发路径）发现三处缺陷，每一处都只在"由调度器拉起、没有人盯着"时才会
暴露；手工分步执行时会被人的介入掩盖。

## 发现

### 一、封面步骤用的是系统 `python3`，而 Pillow 只装在 wewrite 的 venv 里

`make_cover.py` 依赖 Pillow。实测用 `python3` 调用时输出：

```
错误：未安装 Pillow。本脚本需用 wewrite 的 Python 运行：
  .uv-tools/wewrite/bin/python .agents/skills/newsagg-publish/scripts/make_cover.py ...
```

用 `.uv-tools/wewrite/bin/python` 调用则成功（Pillow 12.3.0）。危害不在于"封面做不出来"，
而在于**它失败在第三段**——那时稿子已经写好、简报还没出、这一天已经花掉了分拣与写作
的成本，然后卡在最后一步。而且这个失败与内容质量无关，纯粹是解释器选错。

手工调试时不会遇到它：`run_all.sh` 的发布指引里就写着正确的解释器命令，人会照着敲。
定时任务不经过交互式 shell，没有"记得换个 python"的机会。

### 二、`build_brief.py` 默认按"今天"命名，与 `--date` 的交接指引不一致

`build_brief.py` 的 `--out` 默认值是 `now` 的日期，而不是决策文件里的 `date`。
`run_all.sh` 其余各步都接受 `--date`，于是当 `--date` 不等于当天时（跨零点续跑、
重放历史决策做验证），脚本会生成 `.newsagg/briefs/<今天>.md`，却把指引里的路径写成
`.newsagg/briefs/<DATE>.md`——**指引指向一个不存在的文件**，agent 在第二段拿不到选题包。

修复方式是显式传 `--out ".newsagg/briefs/${DATE}.md"`，让三段共享同一日期。
ADR-0038 已要求"三段必须共享 `--date`"，本缺陷说明**共享日期不能只靠调用方自觉**，
凡是有默认值的地方都必须显式覆盖。

### 三、`collection_runs` 里的"每次新进来多少条"恒为 `?`

ADR-0038 新增 `collection_runs` 供简报 ② 段显示"今天采了几次、每次多少条"。实测
首次采集写入的记录**没有 `kept_new` 字段**，简报渲染成「13:21（新 ?）」——那一行
只有时间没有内容，"多次采集到底采到了什么"仍然不可验证，等于 ADR-0006
「捕捉发酵过程」还是不可观测。

`kept_new` 不能直接用本次采集的 `counts.kept`：第二次采集时赛道预筛仍会"保留 100 条"，
但其中可能全是上一轮已见过的条目——报出 `kept 100` 会把"没有新东西"显示成
"采到 100 条新的"。正确判据是**本次采集时刻新写入的 `first_seen` 数量**。

## Decision

1. **封面解释器在编排器里钉死**：`COVER_PY` 优先取 `$REPO/.uv-tools/wewrite/bin/python`，
   不存在时回落 `python3`。回落是有意的——让错误在封面这一步**显式暴露**，而不是静默
   跳过封面（无封面会被发布门 1 拦下，但那时错误信息指向的是"封面不存在"，掩盖了
   真正的成因）。失败信息里带上实际使用的解释器路径。
2. **`build_brief.py` 的 `--out` 由编排器显式传 `${DATE}`**，不依赖其默认值。
   凡是"默认值取自当前时刻"的参数，在编排器里一律显式覆盖——编排器的日期由
   `--date` 单点决定。
3. **`kept_new` 按 `first_seen == fresh.collected_at` 计数**，而不是取 `counts.kept`。
   该值同时写进 `counts`（供不看 `collection_runs` 的消费者）与 `collection_runs`
   （供简报呈现）。
4. **`collect.py` 的首次采集也走合并路径**（以空池为底）。这条已由 ADR-0038 发现并修复
   （否则首次采集的条目没有 `first_seen`，第二次合并无轨迹可续、`runs_today` 恒为 1）；
   本 ADR 记录的是它的**直接后果**：`first_seen` 缺失会让 `kept_new` 也无法计算，
   两个缺陷是同一处代码路径的两个症状。

## Consequences

- **`COVER_PY` 是环境耦合的显式化，不是硬编码。** 它记录的是"Pillow 只在这个 venv 里"
  这一事实。服务器部署时若 venv 路径不同，回落分支会让失败显式发生——比静默跳过好，
  但那意味着部署清单里必须包含"wewrite venv 就位"这一项。
- **"默认值取自当前时刻"是一类系统性隐患**，不只 `build_brief.py` 一处。无人值守下
  没有人在旁边纠正路径，因此编排器必须把日期当作**显式参数贯穿**，而不是让各脚本
  各自取 `now`。本 ADR 只修了实测踩到的那一处；其余脚本若有同类默认值，应在下次
  改动时一并收紧。
- **`kept_new` 的语义是"本次新进来"，不等于"本次有价值"。** 简报显示「新 0」只说明
  榜单没变，不说明当天没东西可写——事件发酵可以在**同一批条目**上通过热度轨迹体现。
  因此 `hot_history`（ADR-0038 记录但尚无消费者）才是"发酵过程"的完整表达；
  `kept_new` 只是它的一个粗粒度代理。
- **三处缺陷都在"第三段"或"交接边界"上。** 这不是巧合：手工分步执行时，人在段与段
  之间做衔接，会自然地补上缺失的日期、换对的解释器。**无人值守的失败模式集中在
  段与段的接缝上**，因此每新增一段交接，都值得单独跑一次端到端。
