# 开发期 dry-run 模式，以及锁定的运行参数

## Context

调试一条会自动发帖的流水线，必然要反复重跑；而账号是整条链路唯一不可替换的资产（ADR-0001）。若用真实账号调试，试错期的反复填表与提交恰好是风控最敏感的行为模式。

同时，前序决策中有若干**具体数值**被确立但未记录定值（冷却期天数、每日建卡上限），另有一项规则来源需要指明（合规规则）。

## Decision

**一、dry-run 模式。** 开发与验证期全程使用 dry-run：所有阶段真实执行，但发布走到"填完表单、停在发布按钮前"即停止，并截图存证。只有全链路在 dry-run 下验证通过后，才开启真实发布。

实现形态（受 ADR-0025 修正）：发布是单一 Tool `newsagg_publish`，dry-run 由它的 **`dryRun` 参数**控制，**默认为 `true`**，上线后才显式置 `false`。这样既保住单一进程生命周期（Chrome 与流程同生共死，ADR-0023），又保留 dry-run 能力。dry-run 是显式模式，不是"注释掉最后一行"。

**二、锁定的运行参数：**

| 参数 | 值 | 依据 |
|---|---|---|
| 每日成文上限 | 1 篇 | 与每日发布上限一致，产量守恒 |
| 每日发布上限 | 1 篇 | 远低于流传的文章 5/日（该数字无官方来源） |
| 同一观点卡冷却期 | 3 天 | 既跟得紧持续发酵的事件，又与"高度相似内容"拉开距离 |
| 每日新建观点卡上限 | 1 张 | 与成文上限匹配，卡库增长速率可预测 |
| 每日费用上限 | $5 量级 | 超限降级为"只跑分拣不写稿"并告警 |
| 质检复审轮数上限 | 2–3 轮 | 仍不通过则当日弃权并告警 |
| 熔断自动探测次数 | 3 次 | 仍失败转人工 |

**三、合规规则来源。** 平台合规规则维护在仓内（`platforms/`），初期由调研与既有技能（如 `xhs-compliance-check` 的黑名单结构）提炼，后续依据实际的发布被拒或扣分反馈增补。

## Consequences

- dry-run 使"验证"与"冒险"解耦，但也要求 dry-run 路径本身被测试：一个从未真正跑过的 dry-run 模式，其"停在发布前"的保证只是假设。它必须在首次真实发布前被显式验证过（确认它确实没有调用发布动作）。
- 上表数值均为**经验值而非推导值**。它们记录在此以便复核，而不是因为经过了论证。
- 合规规则是仓内人工维护的资产，因此它会**过期**。过期的合规规则比没有更危险——它提供虚假的安心感。这使它成为本设计中最需要定期复核的资产。
- "每日成文上限 1 篇"与"每日新建卡上限 1 张"共同把系统的增长率钉在一个可预测的量级上，这既是成本控制，也是风控措施。
