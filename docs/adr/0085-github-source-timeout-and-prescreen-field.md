# 错误文本会指向错误的方向：github 源的超时与预筛口径

## Context

2026-10-30 的用户提问：「为什么 github 源连续两天全失败」。往下的检查不是计划内的，
但它把这个仓库反复出现的同一类缺陷又抓出来一次——**观测失真比故障本身更贵**。

## 发现

### 一、失败是真的：github 是唯一要走代理的源

直连 `https://github.com/trending` 在这台机器上不通：一次 0.4 秒内 TLS 断开，一次挂满
15 秒超时。所以 `reference/DailyHotApi/src/index.ts:10` 那段本机补丁是必需的
（「github 源直连不通，必须走本机 Clash」，靠 `ProxyAgent` 走 `127.0.0.1:7897`）。
其余六个源（头条 / 36氪 / 掘金 / CSDN / IT之家 / 少数派）都是国内站，直连即可——
**github 是七个源里唯一有外部依赖的**。

Clash 本身没重启过（`verge-mihomo`，10-26 20:33 起），7897 在听。问题在出口：
代理接受了 CONNECT 隧道（`HTTP/1.1 200 Connection established`），随后到 github 的
TLS 握手被中断（`Recv failure: Connection was aborted` / `schannel: failed to receive
handshake`）。也就是说，代理节点到 github 的路是**间歇性**通的——22:22 手动敲一次
`/github` 成功返回 15 条（2.4 秒），23:30 再敲就握手失败。

### 二、为什么失败从 10-29 开始，而不是更早

github 的路由有 **24 小时缓存**（`src/routes/github.ts:81` `ttl = 60 * 60 * 24`）。
最后一次成功取数是 10-28 21:00 那一轮（所以 10-27、10-28 的候选文件里没有 github 失败
记录）。缓存在 10-29 21:00 前后过期，此后每一次采集都落到「回源」，而每一次回源都撞上
代理握手失败。**缓存把间歇故障变成了「每天都在同一个环节失败」**，看起来像"某个源挂了"，
实际上只是它每天只有一次暴露机会，而那一次撞上了。

### 三、记下来的错误文本是错的

`reference/DailyHotApi/logs/error.log` 里，10-30 三次采集的原话是：

```
08:00:56  ❌ [ERROR] fetch failed  →  所有尝试请求失败！
13:00:22 / 13:00:34 / 13:00:47  第 1/2/3 请求失败: fetch failed
18:00:24 / 18:00:36 / 18:00:48  同上
```

服务端**重试 3 次（`github.ts:112` `maxRetries = 3`）、每次 abort 在 20 秒（`:119`）**，
最坏要 60 秒才回话。而采集器的客户端超时是 20 秒（`collect.py` 的 `--timeout` 默认值），
于是它永远先弃权，把 `timed out` 写进 `failures` ——**真原因 `fetch failed` 一次都没进过
候选文件与简报**。

这条和 ADR-0057（假的绿色）／ADR-0081（空转的闸）是同一族：**系统没有说真话，
不是它出错，是它说完错话之后还能正常退出**。区别在于前两次骗的是"通过与否"，
这次骗的是"为什么失败"——而"为什么失败"直接决定了人去查代理还是去查代码。

### 四、更麻烦的一层：即使成功，它也一条都进不了池

10-27、10-28 的 `source_meta.ok` 都是 `True`，而 github 进池条目都是 **0 条**。
原因不在网络，在预筛：`niche_prescreen` 只匹配 `title`，而 GitHub Trending 的
`title` 是**英文仓库名**（`claude-mem` / `OpenMausBot` / `ziwei-doushu` / `skills`）。
中文关键词表（开源、前端、架构、AI…）基本命中不了仓库名，只有像 `claude-mem`
这种带模型名的会命中 `Claude`。

所以"修好它"和"让它有用"是两件事。**在预筛改掉之前，「github 到底值不值得留」
这个问题根本测不出来**——你会拿着一个 0 产出的源，把所有注意力放在它的失败率上。

## 决定

1. **超时按源覆盖**（`SOURCE_TIMEOUTS = {"github": 75}`）。75 秒 = 3 × 20 秒 + 余量，
   保证客户端**活得比服务端的重试预算长**，这样服务端最终返回的错误能真正落到
   `failures` 里。代价是 github 真挂时该轮采集多等约 55 秒，一天三次最坏多 2 分 45 秒。
   这是**确定性成本换可诊断性**，我认为值：一个说不清为什么失败的源，等于每天都要人肉进日志。
2. **预筛对 github 额外匹配 `desc`**（`DESC_MATCH_SOURCES = {"github"}`），并让
   `normalize_dailyhot` 保留上游本来就给了却被丢掉的 `desc` 字段。
   **只对 github 开**，不做全源：热榜的 `title` 就是内容本身，`desc` 常常是不相干的
   摘要，全源一起匹配会把"消费电子评测"因为提到 AI 灌进池子——预筛精度靠的就是这条边界。
3. **不退役这个源。** 改完当场实测：`--sources github` 单采 15 条、**9 条进池**
   （`claude-mem`、`impeccable`、`OpenBot`、`skills`、`browser`、`thinkrail`…），
   改之前是 0。先有产出，再谈去留。

## 未做

- **没有加"代理挂了"的健康检查。** 现在能读出来的只有：服务端日志里 `fetch failed`，
  客户端 `failures` 里同样的文本。要区分"代理节点不可用"与"github 站点故障"，
  得让采集层去探一个第二目标（例如 `https://api.github.com/rate_limit`）——
  那是新增一条外部依赖，不该顺手加。
- **没有加"连续两次失败才报警"。** 这个仓库对"每日必然触发的告警"有明确警惕
  （ADR-0006/0021/0031），而 github 的失败本来就是间歇的——阈值定多少，
  现在没有任何数据支撑（只有两天的样本）。
- **没有把这件事接进简报的自动告警。** 简报②段只会印「失效源：github」，
  和它过去印过的那几次一模一样，看不出这次是代理、上次是别的。人要知道细节，
  目前只能自己进 `logs/error.log`。

## 边界

`desc` 匹配能命中的前提是**赛道词表里有英文词**（AI / Agent / Claude / Gemini / IDE /
API / SDK…）。`platforms/niche.txt` 归人所有（ADR-0018），如果哪天它被改成纯中文词表，
github 会**静默地重新变成 0 产出**——而这一次不会有任何报错，因为"成功但全被筛掉"
和"成功且有产出"在账本里长得一样。这是本 ADR 引入的新可失效假设，写在这里备查。
