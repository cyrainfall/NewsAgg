# 误发一次就要说一次：账本里的字段必须有人读，否则它等于没记

## Context

2026-10-25 我为验证「每日 1 篇」硬闸的覆盖通道，用 `--allow-daily-override` 跑了一次真发——我以为覆盖只会绕过闸口然后停下，实际它绕过闸口后继续执行了完整发布流程，**真的发出了一篇重复文章**（gid `7700497729948041762`，与 10-24 那篇内容完全相同）。

ADR-0059 记录了这件事，并做了两件补救：账本里补录一条 `accidental: true`、`needs_human_delete: true` 的记录；`count_published_today` 跳过它，所以它不占当日额度。

然后今天 21:00 主流程跑完，简报出来了，第⑤段里没有这一条。

**ADR-0059 的 Decision 三写的是「误发不占额度，但必须留在账本里」。留在账本里、没有消费者，等于没记。** 这是本仓同一族缺陷（「记录了但没有实现」）的第七次，也是最短命的一次——上一份 ADR 写完的第二天就复现了。

它比前几次更难看的地方在于：系统完整地知道「我误发了一篇、这篇需要人删」，而唯一能处理这件事的人（简报的唯一读者）从头到尾没被告诉。所以那篇重复文章在平台上一挂就是一整天，没有人动手。

## Decision

**简报第⑤段必须列出未处理的误发，直到账本里出现终态字段。**

与微头条泄漏（ADR-0047/0055）同一套机制，因为它们是同一类事实：平台侧删不掉、只能人工处置、而且不会自愈。

- 判据：账本里 `accidental` 为真且**没有** `deleted_at`。
- 列出内容：日期、《标题》、gid——gid 是人工去后台找那一篇的唯一入口。
- 处置说明写进简报：「创作中心 → 内容管理 → 找到该篇 → 删除」，然后往对应记录写 `"deleted_at": "<日期>"`。
- 明确禁止的写法：**不要把 `accidental` 改成 `false`**。改 `deleted_at` 是记录事实，改 `accidental` 是让账本说谎——ADR-0055 在微头条那条上犯过同一个错（当时只有「已删」一个终态，于是「决定保留」被记成了「已删除」）。
- 进入条件只看字段，不看日期：误发一旦发生就永久存在，只在当天提醒一次等于让它消失。

## 为什么不是「发布流程加校验」

第一反应是让 `publish.py` 在发布前检查「今天是否已发过同标题的文章」。但这条已经在门 0.5 做了（`count_published_today`），而这次误发**恰恰是故意绕过它的**——覆盖通道存在的意义就是绕过。

真正失效的不是校验，是**绕过之后没有人知道**。所以修在「让人知道」这一侧，而不是在「让人绕不过」那一侧：覆盖通道必须保留（上一篇可能是误发，需要人工补发），但绕过的事实必须持续可见。

## 一条更普遍的判据

ADR-0059 已经写下「决定里出现『X 进 Y』时，必须能在 Y 的代码里找到读 X 的那一行」。这次补上另一半：

**加一个账本字段时，必须同时回答「谁会读它，读不到会怎样」。**

只写字段不写读者，字段就只是给自己看的笔记。而这个系统的所有输出都指向一个人——简报的读者。任何「需要人做的事」如果没进第⑤段，就等于没有交出去。

顺带一提：`tests/test_brief_accidental.py` 钉住了四条渲染行为（未处理要列出、终态字段名正确、处理后停止提醒、正常记录不误报）。第一条的意义不是「代码对不对」，是「这条信息有没有真的到达人」。

## Consequences

- **重复文章不会被漏掉。** 在人工删除并在账本写 `deleted_at` 之前，简报每天都会列出它。代价是每天多一行——这是可接受的，因为它是「有一件只有你能做的事没做」。
- **账本多一个终态字段 `deleted_at`。** 与 `leak_resolved_at` / `leak_accepted_at` 并列，三者语义不同：前两者区分「删掉」和「决定保留」，后者只表示「删掉了」（误发没有「决定保留」这个选项——重复文章留着没有任何好处）。
- **简报第⑤段的长度随历史债务增长。** 目前它同时承载：熔断待处理、微头条泄漏、误发、运行失败、降级、信源体检、封面警告。这一段的定义是「需你介入」，而「需要人做的事」本来就会积累；如果它长到没人读，那说明债务真的太多了，这本身是信息。
- **没有自动重试、没有自动删除。** 平台明令禁止重复发文，而 CLI 没有删除能力——这两件事都只能由人做。系统能做的只有一件事：不让人忘记。
