# 台账的计数键从「议题 × 天」扩成「议题 × 报道」

## Context

ADR-0083 把建卡门槛从「预测可复用性」换成「同一议题第 2 次出现」，计数由脚本按**天**
去重。这条规则在 2026-10-29 第一次跑起来就露了一个边角：台账里那两条议题
（`AI 时代如何评价程序员的能力`、`AI 输出致害的责任归属`），10-30 候选池里出现的
**仍是同一 URL 的原报道**——热榜上的文章挂了没掉，第二天被重新采到、重新分拣看见。

按天计数，它们第二天就该凑够 2 次、被逼着建卡。而「第二次出现」的全部意义是
**不是孤例**；同一篇文章挂两天证明的是热榜没换，不是议题复发。拿它当证据，会建出
一张没有第二份材料的卡。

## 决定

计数键加一维：**议题 × 报道**。

- `no_card_available[]` 的每个条目新增可选字段 `urls`（这一次是靠哪几条报道看出来的）。
- 台账每个议题维护 `urls_seen`（已见过的报道集合）。
- 判据：**这一次带来了没见过的 URL，才算新的一次出现**；URL 全见过，只更新
  `last_seen` 与事件列表，`times_seen` 不动。
- 两重去重并存：同一天出现两篇不同报道仍算一次（按天）；跨天重复同一篇不算（按报道）。
- **没给 `urls` 时退回按天计数**。这一点是刻意的：老决策没有这个字段，若默认
  「没有 URL ＝ 不是新出现」，所有历史计数会静默变少，而台账的全部价值在于可信。
  判据用的是**归一化之后**的 URL 列表——调用方填了个空数组或全是非 http 值，
  也退回按天，不能因为填了个空就把这一次丢掉。

顺带把事件记录加上 `counted` 标记：翻台账时能一眼看出哪几次是真计入的、哪几次只是
「又看见了同一篇」。这是事后复核这个门槛的唯一线索。

## 为什么不是「按 URL 判重就够了」

只按 URL 会让一个议题在**同一天**被多篇报道连续「计两次」（白天三次采集、21:00 主流程
各写一次决策，各自的 URL 可能不同）。门槛是「不是孤例」，一天之内看到十篇同向报道
仍然是同一天的观察。天与报道这两维缺一不可，所以是「天 × 报道」，不是替换。

## 后果与遗留

- 台账里已有的三条议题按当时的候选池**回填**了 `urls_seen`（1 / 2 / 3 条）。不回填的话，
  它们下一次出现会被当成「全是新报道」而 +1，等于修复对它们不生效。
  回填脚本是一次性的（`tmp/` 下，不入库）：URL 不靠记忆，按标题从
  `.newsagg/candidates/<日期>.json` 里取真值。
- **阈值仍是 2，没动**。ADR-0083 说「先跑 30 天再用真实分布定阈值」——这次只改了
  计数的**单位**，没有改门槛。真正该重估的是「30 天里有多少议题能被数到 2」，
  那要等台账攒够。
- **SKILL.md 已同步**：`urls` 写进输出形状与说明。模型不填，这层保护就退回按天
  ——而它不会报错，所以文案得写清楚「要填」。
