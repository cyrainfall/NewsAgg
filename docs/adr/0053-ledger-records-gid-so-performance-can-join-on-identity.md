# 发布账本必须记 gid：标题不是身份，它会被平台改写

## Context

ADR-0051 修掉「标题被输入框吞字」之后，反查按平台实际标题查得到了。但同一份
账本还有第二个消费者：**循环 C 的表现数据回路**。它要把平台上的作品关联回本地
`outputs/<slug>.md`，靠的是 `performance.py:local_title_index()`——一张
**标题 → slug** 的表，账本优先、成稿兜底。

2026-10-21 那篇的平台标题是「老板叫停AI裁员，中间层位已经换成外包」，
而账本里的 `title` 是成稿标题「…中间层**岗**位…」。于是：

- `title_index` 里查不到 → `matched: false`、`ours: false`
- 这篇**既不进基准序列，也不消耗冷启动豁免的 5 篇额度**
- 表现数据里有它（`gid 7699135881185149480`、metrics 全 0），但关联断了

这和 ADR-0051 是同一根因的**下游症状**：标题不是身份，它是**可变的表现层**。
发布时会被吞字、本人事后也可能到后台改标题——`local_title_index()` 的 docstring
里早就记着「本人改过标题后账本 title 与平台 title 不同」这件事，当时的解法是
「账本优先」，但那只是在假设**账本里的标题等于平台上的标题**，而吞字打破了这个假设。

## 发现

### 一、gid 才是身份，而且它一直就在手边

反查时 `content list` 的 payload 里每条都有 `gidStr`。发布链拿它数过
`verify_kinds`（ADR-0047），却**没有把它写进账本**——所以循环 C 只能退而用标题。

### 二、修复分两步，缺一不可

1. **往后**：`publish.py` 反查成功后用 `find_gid()` 取出 gid 写进账本；
2. **往前**：历史 5 条账本没有 gid，但它们的作品还在平台上、标题也没被改过，
   可以按标题反查回填一次（已做，5 条全部回填成功）。

只做第 1 步，历史数据仍然关联不上；只做第 2 步，明天又会缺。

## Decision

### 一、`publish.py` 反查成功时记录 `gid`

新增 `find_gid(payload, title) -> str | None`，判据与 `count_title_kinds()` 共用
同一套「文章 vs 微头条」投票（gid 位数 / URL 形态 / `content` 非空），
同一标题下有多条时**优先返回文章那条**（微头条泄漏时不能把微头条的 gid 当文章）。

### 二、`performance.py` 改为「gid 优先、标题兜底」

`local_title_index()` 返回值从 `(index, meta)` 变为 `(index, by_gid, meta)`；
账本的 `title` 与 `title_on_platform` **都**收进标题索引（吞字时只有后者能命中）；
匹配时先查 `by_gid`，查不到再查标题。

标题兜底必须保留：历史记录在回填之前没有 gid，而 `reports/performance.jsonl`
是**跨环境保留的入库文件**，里面已有旧记录。

### 三、历史账本回填 gid

用一次性的脚本把 5 条老记录的 gid 从 `content list` 补进去，并标
`gid_backfilled_at`。这不是常规流程——**一次性修数据，不是长期机制**。

## Consequences

1. **吞字不再导致表现数据丢一篇**：实测回填后 `by_gid: 6`、`unmatched: []`、
   `articles_matched: 6`（此前是 5，那篇被吞字的被判未匹配）。
2. **本人事后到后台改标题也不再断链**：gid 不变，标题怎么改都匹配得上。
   这比「账本优先」强——后者只在标题没被改的前提下成立。
3. **`title_on_platform` 与 `gid` 现在是账本里两个必须存在的字段**：前者让反查
   查得到（ADR-0051），后者让表现数据关联得上（本 ADR）。缺任一，链路的某一段
   就会静默降级。**`publish.py` 的 dry-run 分支不产生 gid**（草稿不在
   `content list` 里，ADR-0032），所以 dry-run 记录的 gid 永远是 null——这是
   预期，不是缺陷。
4. **回填脚本没有入库**：它是一次性操作，跑完即弃。若将来发现还有旧记录缺 gid，
   需要重新写一遍——这是接受的小代价，因为 `content list --limit 20` 只有最近
   20 条，更老的补不回来。
5. **同类风险**：`brief.py` 的表现段落、`publish.py` 的 `count_title_kinds()`
   仍以标题为键。前者只做展示（标题错就显示错的标题，可接受）；后者是发布当次
   的即时计数（此时标题刚从输入框读回，是最新的），都不需要 gid。**唯一需要
   稳定身份的是跨时间的关联，而那里现在用 gid。**
