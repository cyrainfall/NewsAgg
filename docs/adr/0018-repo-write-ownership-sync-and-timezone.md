# 仓的双写所有权、同步方式与时区

## Context

系统在云上自动 `commit + push`（Q82），而本人也会修改教学副本并 `push`（Q83）。两个写入者操作同一个仓，若不划定所有权，冲突是必然的；而 Q83 的学习信号又**依赖**系统能看到本人的修改，因此系统必须在每次运行前拉取。

同时，云服务器时区常为 UTC，而"当晚发布"与"次日简报"里的时间都是本人当地的（Asia/Shanghai）。依赖服务器本地时区会在换机器或重建时静默出错。

## Decision

**一、文件所有权划分**（使两个写入者的写入不相交）：

| 路径 | 写入者 | 说明 |
|---|---|---|
| `knowledge/cards/` | 系统 | 建卡、追加修订（受新建门槛与每日上限约束） |
| `outputs/` | 系统**写一次**，之后归本人 | 发布时写入，此后不再触碰 |
| `reports/` | 系统 | 简报 markdown |
| `.wewrite/`（除 config.yaml） | 系统 | 运行时状态（风格、历史、范文） |
| `style/` | **本人** | 系统只提议（写入 `reports/`），不直写 |
| `platforms/` | **本人** | 合规规则需人工复核以免过期 |
| `reference/`、`config.yaml`、浏览器会话 | 不入库 | 见 ADR-0012 / 0015 |

**教学副本是"写一次后移交"而非共享文件**：系统在发布时写入 `outputs/`，此后永不修改它。因此它不存在并发写入，而本人对它的后续修改就是干净的 diff 信号。

**该次写入的 commit 同时充当"发布快照"**——即风格学习的比对基线（见 ADR-0026）。因此 `outputs/` 的历史应视为**不可重写**：rebase 或 force push 会破坏基线的可解析性。

> **修正（ADR-0036）**：commit 不足以充当基线——本人改稿 push 后，"最后一次提交"就是改稿本身，基线随之错位。
> 发布快照现由 `publish.py` 在发布时把指纹写入发布账本（`git_blob` 指向当时的内容），不再事后推断。
> `outputs/` 历史不可重写的约束仍然有效（它保证 blob 可解析）。

**二、同步方式**：云端每次运行前 `git pull --rebase`，运行后 `commit + push`。因写入不相交，冲突几乎不会发生；一旦发生，**熔断告警且不自行合并**——自动解决冲突可能静默丢弃本人在风格或合规规则上的修改。

**三、时区固定为 `Asia/Shanghai`**，在仓内显式声明，不依赖服务器本地时区。

## Consequences

- `style/` 归本人所有意味着**风格资产的更新需要本人手动应用**系统的提议。这削弱了"越写越强"的自动化程度：系统只能指出"这里似乎有你的偏好规律"，不能直接改风格库。这是有意的，因为风格是本人的身份，不应由模型自说自话地改动。
- 浏览器会话（Chrome profile 内的登录 cookie）按 Q81 的同一原则排除出库。因此**云服务器上的浏览器 profile 是不可丢的运行时资产**——它不在 git 里，丢失即需重新人工登录（Q84 的首次扫码）。
- "冲突即熔断"意味着一次真实的合并冲突会让当天不发文。这是可接受的：冲突表明所有权划分被破坏了，值得人工看一眼，而不是让自动合并悄悄掩盖。
- 固定时区使调度语义在任何服务器上一致，但也意味着若本人换了时区，锁定值需要手动更新。
